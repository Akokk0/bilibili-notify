# 没有实现者的接口不造

**1.0 里没有实现者的扩展点，接口与登记表都先不造。** 等第一个真实现者出现，再连同配套的问题一起设计。这是活规范，可以直接改，但加条、改条要主人拍板。为什么这样定见 [ADR-0031](../../adr/0031-commands-and-devtools.md) 决策 1 与 [ADR-0012](../../adr/0012-extensions.md) 决策 13。

## 规矩

1. **接口加进契约、登记表加进核心之前，先数实现者。** 内置的、拓展的都算；一个都没有就不造。设计文档里写了名字、代码里还没造的，也照此办。
2. **不为「以后可能有人要」留口子。** 一个实现者都没有的登记表，不先建空的。
3. **等第一个实现者出现，再连同配套问题一起设计。** 只有真实用例才知道接口该长什么样，事先设计就是在猜。
4. **没造的东西，把「什么时候再看」写进文档。** 写到 `docs/1.0/construction-plan.md` 的「以后再说」，或 ADR 的「仍未决」，别让它消失。
5. **契约只能窄面加宽，不能反过来。** 拿不准要不要给拓展多开一格，就不开（ADR-0012 决策 13）。

例：`login` 改成核心的通用指令 `login [来源]` 以后，1.0 里没有来源自带的指令，`CommandProvider` 没有实现者，所以登记表不造。指令重名怎么处理这类配套问题，等第一个要自带指令的拓展出现时一起定。

- 对：指令全是核心的，以 `CommandDef` 交给指令框架；文档里写明「`CommandProvider` 先不造」和再看的时机。
- 错：先造一张 `CommandProvider` 登记表和重名规矩，等着以后有人用。

## 边界与例外

- **有实现者、只是不对拓展开放的口子，不归这条管。** 那是「开不开放」的另一类决定，理由不同，按各自的 ADR 走。
- **暂时不对拓展开的口**（如 `linkResolver`、`aiTools`）核心里已有实现者（B 站在用），只是清单先不开；不是「没有实现者」。
- 这条是纪律，不是禁令：出现了真实现者，就该造。

## 怎么钉住

靠审查。没有守卫。审查逐条看：

1. 新加的接口、登记表、可选参数，现在有几个实现者、几个调用方；为零就退回。
2. 设计文档里新写的扩展点，有没有对应的真实用例。
3. 决定不造的，有没有写进「以后再说」或「仍未决」，并写清什么时候再看。
4. 给拓展开新口子之前，有没有先按 ADR-0012 决策 13 问一次「不开会怎样」。
