# 指令系统参考(独立端)

主人在 IM 私聊里敲的那套指令:入站链路、指令表、参数模型、可配置项。CLAUDE.md 的渐进式披露目标之一。

**只覆盖独立端。** koishi 端的 `bili.*` 与 AstrBot 的 `bn` 各有框架自带的命令系统,不动、也不强行统一 —— 那两端的用户已经形成肌肉记忆。

## 三条约束

底下几乎每个决定都能回溯到这三条,改动前先对一遍:

1. **这条私聊同时是主人正常说话的地方。** 它不是一个专用的命令行终端 —— 任何「对认不出的输入给回音」的设计都会让主人没法在这儿好好聊天。
2. **通道对面是 B 站账号与推送控制权。** 任何回音都是接口指纹,试探者靠报错差异就能摸出指令表。
3. **只有 onebot / qq-official 收得到回复**(`INBOUND_CAPABLE_PLATFORMS`)。webhook 天生没有回程。所以指令是**增量入口,不是 Dashboard 的替代** —— 每个能力在网页上都得有一份。

## 模块清单

全部在 `apps/server/src/runtime/`,接线在 `apps/server/src/index.ts`。

| 文件 | 角色 |
|---|---|
| `inbound-message.ts` | `extractPrivateMessage` —— 平台事件帧 → `InboundPrivateMessage{userId,text}`,平台差异到此为止 |
| `command-dispatcher.ts` | 鉴权、四道门、路由、触发词查重(`effectiveAliases` / `command()` 注册助手) |
| `command-params.ts` | 签名解析 `parseSignature` + 入参解析 `parseArgs` + 从签名推 handler 入参类型的 `Values<S>` |
| `command-help.ts` | `renderUsage` / `renderHelp` —— 纯函数,私聊帮助与面板卡片共用 |
| `command-suggest.ts` | `suggestCommand` —— 未知指令的近似建议 |
| `mute-state.ts` | 静音状态(读时判定,无定时器) |
| `mute-command.ts` / `status-command.ts` / `report-command.ts` / `login-command.ts` | 四条指令各自的业务实现 |
| `roast-command.ts` | 审批 y/n,以 `ConfirmationWindow` 的身份挂进分发器 |
| `routes/commands.ts` | `GET /api/commands` —— 把注册表列给面板 |
| `routes/command-alias-guard.ts` | `checkCommandAliases` —— 保存配置时的别名查重,挂在 `routes/globals.ts` 的 PATCH 上 |

`help` 那条不单独成文件,直接在 `index.ts` 里注册 —— 它要列出**包括自己在内**的全部指令,得拿到那张表本身。

## 入站链路

```
平台事件帧
    ↓  extractPrivateMessage        (平台差异到此为止)
InboundPrivateMessage {userId, text}
    ↓
┌─────────────────────────────────────────────────┐
│ ① 鉴权门 —— 必须在解析之前                        │
│    不是私聊 / 不是主人 → 静默返回,零回音          │
└─────────────────────────────────────────────────┘
    ↓  (只有主人到得了这里)
┌─────────────────────────────────────────────────┐
│ ② 待确认窗口 —— 有待确认项时才开                  │
│    命中 y/n → 交给确认流,不进指令表               │
└─────────────────────────────────────────────────┘
    ↓
┌─────────────────────────────────────────────────┐
│ ③ 总开关 —— 排在确认流之后                        │
└─────────────────────────────────────────────────┘
    ↓
┌─────────────────────────────────────────────────┐
│ ④ 前缀闸 —— 不带前缀的直接放行回聊天              │
└─────────────────────────────────────────────────┘
    ↓
┌─────────────────────────────────────────────────┐
│ ⑤ 路由 + 参数解析(声明式签名)                    │
│    未知指令 → 提示 + 近似建议;参数不合法 → 报错   │
└─────────────────────────────────────────────────┘
    ↓
   handler(各指令的业务实现,归各自的服务)
```

三处顺序是**语义**,不是实现细节:

- **鉴权不能写成路由里的中间件** —— 它必须先于解析发生,否则「未知指令」的回音会在鉴权之前漏出去,而那正是约束 2 要防的。
- **总开关排在确认流之后** —— 「关掉 = 整条链路只剩确认流」。一起关掉的话,主人关一下指令,手里那份等审批的周报就再也批不掉了。
- **前缀闸排在路由之前** —— 不带前缀的一律当聊天,连「没有这条指令」都不说。

两个入口共用同一份鉴权与路由:`handle(frame)` 给 OneBot 那种原始帧,`handleMessage(msg)` 给网关已经解析好的 qq-official。各写一份的话迟早有一边把「不是主人也放行」写漏。

## 指令表

**主名一律英文,中文进别名。**两者等价,主人敲哪个都行 —— 但主名要进代码、进日志,中文主名会让 `spec.name` 与 handler 里的字符串常量全变成中文。

| 指令 | 内置别名 | 签名 | 说明 |
|---|---|---|---|
| `help` | 帮助、? | `[name:string\|指令名]` | 不带参数列出全部;带参数给单条详情 |
| `status` | 状态 | — | 登录态 / 上次抓取 / 推送通道 / 渲染排队 |
| `mute` | 静音、免打扰 | `<duration:duration\|时长>` | **全局**静音,到期自动恢复 |
| `report` | 周报 | `[days:number\|天数]` | 按面板上的审批开关走 |
| `login` | 扫码、登录 | — | 重新登录 B 站,二维码只发主人私聊 |

匹配**大小写不敏感** —— 手机输入法会把 `/mute` 自动首字母大写成 `/Mute`,而主人屏幕上那行字和帮助里印的看起来一模一样。按触发词长度切片再比,不用 `toLowerCase().startsWith()`:某些字符小写化会改变长度(İ → i̇),那样剥长度会错位。触发词后面必须是边界(到头或空白),不做前缀模糊 —— 「静」不该命中「静音」。

### 静音

- **状态** = `globals.mutedUntil`(epoch ms,`0` = 没静音)。落盘换来「重启不解除」与「网页上看得见」。
- **判定** = 读时现算 `now < mutedUntil`,**没有定时器**。到期不是一个会发生的事件,只是同一个比较的结果变了 —— 于是重启 / 时钟跳变 / dispose 时序全都不用管。
- **闸门** = `BilibiliPush` 构造时注入的 `muted: () => boolean`(`engines.ts` 接的是 `muteState.isMuted()`),挡在 `broadcastToFeature` 里,和 quietHours 并排。一道闸盖住全部 feature。
- **不挡主人私聊** —— 指令回复(包括「静音到几点」这句本身)和运行错误告警都走那条路。一起挡掉的话,静音生效的唯一证据恰好被静音吞了。
- **定时周报 / 锐评不受静音管**。它们走 `push.sendToTarget`,不经 `broadcastToFeature`。这一条写进了 `mute` 的 `details`,主人敲 `help mute` 看得到 —— 不写的话他静音期间收到一份周报,只会以为静音坏了。
- 回复里带**恢复时刻**,跨天时带日期。静音是个无声状态,主人过一会儿发现没推送,分不清是自己静音了还是系统挂了,而这两件事的处理方式完全相反。

只做全局,没有按 UP 主分别静音 —— 那要动推送路径的判定,工作量差一截。

### 状态

**就四项**,挑的都是「不正常时才有救的东西」:登录掉了 / 不抓了 / 推不出去 / 卡住了。别再往里加订阅数、今日推送数之类 —— 这条消息是在手机上看的,长了就没人读。静音只在真静音时多占一行(它是「怎么没动静」的第一嫌疑)。

取数与渲染分开(`StatusReport` 是纯数据,`renderStatus` 是纯函数),否则要验一句文案就得先起半个服务端。「上次抓取」只记**成功**不记尝试 —— 连着失败三小时的系统若报「1 分钟前抓过」,这一项就从「还在跑吗」的答案变成了骗局。

### 周报

五条里**唯一会花钱**的一条:每跑一次都是一次真实的 AI 调用,几十秒起。照 Slack 的 3 秒规则处理:

```
/周报  →  立刻 ack「在生成了，稍等～」
       →  跑着时再敲 → 回「还在跑呢」    ← 防抖,不跑第二次
       →  完成 → 按审批开关走(预览等 y / 直接发)
```

**防抖不是体验问题是花钱问题** —— 没有 ack 的话主人会以为死了反复敲,每敲一次都是一次真实的 AI 调用。那道闸在**失败路径上也必须松开**(`finally`):一次异常锁死它的话,主人得重启服务才能再要一份周报,而他绝不会想到是这个原因。面板上的「试一次」是另一条路,不共用这道闸。

天数的范围校验在指令里,不在 parser 里 —— 那是这条指令自己的业务规则,parser 只管格式。审批开着时,草稿连同「回复 y <id>」由调度器自己私聊出去,指令层**不再补一句**(同一件事说两遍,两份措辞迟早跑偏)。

### 扫码

- **二维码只发私聊。** 发进群等于公开征集「谁来当我的 B 站账号」。这条由 `sendToMaster` 的强制私聊保证(onebot adapter 拿不到 userId 时直接报错,不会回落到群);指令层保证另一半 —— **发不出去必须说出来**,不然主人就盯着手机等一个永远不来的码。
- 真正的风险不是泄漏而是**污染**:攻击者若能触发扫码并抢先扫,系统就跑在他的账号上。触发权由鉴权门挡着。
- **必须手动。** B 站二维码 180 秒过期,所以不能做成「检测到失效就自动推一个码」—— 主人两小时后看手机拿到的是废码,反而以为系统坏了。

> 对照:备份该**自动**(怕你忘),扫码必须**手动**(码会过期)。
> **该自动还是该指令,不取决于重要性,取决于产物有没有时效。**

## 参数模型

签名借 koishi 端的写法,跨端认知一致;但**只写参数部分**,不含指令名 —— 指令名与别名都在注册表里,而别名是主人可配的,让它再出现在签名里就得两处同步。

```
<参数名:类型|显示名>   必填
[参数名:类型|显示名]   可选
```

**参数名与显示名分开**,因为这两个名字面向的对象不同:参数名进代码(`values.duration`),显示名进报错(主人在手机上收到的「缺少参数「时长」」)。合成一个就得二选一牺牲。`|显示名` 可省,省了就用参数名;它不必是翻译,写成「第几页（从 1 开始）」也行。

| 类型 | 接受 | 备注 |
|---|---|---|
| `string` | 一段不含空白的文本 | |
| `number` | 整数 | 越界 / 非数字 → 友好报错 |
| `duration` | `3h` `30m` `2小时` `30分钟` `1天` | 中英文单位都收,长单位在正则里排前面(否则「分钟」会被「分」吃掉半截) |
| `text` | 吞掉剩余全部文本(含空白) | 只能放最后一个位置 |

签名在**注册那一刻**就解析掉,不等主人敲指令时才解析 —— 签名是代码里写死的,写错了该在启动那一刻炸。四条硬规则都在 `parseSignature` 里抛:类型不认识、`text` 后面还有参数、必填排在可选后面、参数名里写了竖线(竖线曾经写在冒号左边,写反了会让 handler 永远读到 undefined)。

**必填必须在可选之前**不只是风格:`Values<S>` 那套类型推导按这个顺序解析签名,支持交错会直接撞 `Type instantiation is excessively deep`。类型和运行时不能各说各话,所以运行时也钉死。

解析失败**不进 handler** —— parse 与 execute 分离(Cobra/oclif 的做法),handler 拿到的永远是已校验、且**类型由签名推出来**的值(`command()` 注册助手留住签名的字面量类型,handler 里不用写断言)。多余的参数不静默丢掉,照样报错 —— 丢掉的话主人会以为它生效了。

### koishi 踩过的坑,以及这里怎么挡的

koishi 的指令系统近一年没有新设计,提交全是 bug fix —— 而**它反复出错的位置就是参数解析的固有难点**。动这一层之前先对一遍:

| koishi 的修复 | 这边的处置 |
|---|---|
| `fix: short option not properly parsed`(2025-05) | 不做 flag/option(`-c` 那种),天然绕开 |
| `fix: greedy + strict options 边界`(2024-11) | `text` 吞掉剩余全部,边界钉死为**只允许放最后一个位置**,`parseSignature` 里抛 |
| `feat: fix regression of command alias args`(2024-08) | 最容易踩的一条。别名在这里是**用户可配**的,风险比 koishi 的硬编码别名更高。匹配时剥掉的是**实际命中的那个触发词**的长度,不是主名的;`command-dispatcher.test.ts` 的「别名带参数」用例钉住它 |
| `fix: only capture quote with root argv`(2024-08) | **不支持引号**。现有参数(时长 / 天数 / 指令名)都不含空格,真需要再加 |

> 顺带记一句方向:**cordis 不含指令系统**(它是 Context / 服务 / 生命周期 / HMR 那层),二十个 cordiverse 仓库里没一个沾指令。要参考只能看 `koishi/packages/core/src/command/`。

## 确认流

`y`/`n` 不是普通指令,而是**待确认队列**的回应,以 `ConfirmationWindow` 接口挂进分发器:

```ts
interface ConfirmationWindow {
	isWaiting(): boolean;
	tryHandle(msg: InboundPrivateMessage): Promise<boolean>;
}
```

分发器**故意不知道** y/n 这个语法 —— 它只问「有待确认的吗」「你消费了吗」。让通用设施去认某一条具体指令的语法,就把依赖方向倒过来了。目前唯一的实现是 `roast-command.ts` 的锐评 / 周报审批。

**监听窗口有状态 —— 只在真有待确认项时才认。**没有待确认项时,`y` 只是个普通字母,压根不进指令层。这也解释了**为什么 y/n 不需要前缀**:它只在系统正等着你回答时才有意义。

多份待确认时必须带 ID(`y a3f`);不带 ID 又有多份时,回一句列表并给出照抄示例。猜错的代价是把不该发的那份发出去了。

审批本身的三条判定(群消息不算 / 别人发的不算 / 话里带个 y 不算)在 `roast-command.test.ts` 里钉着,动这一层时那些断言一条都不能松。

## 可配置项

存在 `globals.commands`(顶层,同 `roastSchedule` / `mutedUntil`),schema 在 `packages/internal/src/schema/commands.ts`。系统页的「私聊指令」卡片是 `apps/web/src/components/commands-settings.tsx`。

| 配置 | 默认 | 校验 |
|---|---|---|
| `prefix` | `/` | 允许为空(见下);不允许纯空白。`"bn "` 这种带尾空格的是**合法**的,所以判定不能简单地 trim 完比空 |
| `aliases[指令主名]` | 见指令表 | 别名不能为空串或带首尾空格(入站文本会被 trim,留着只会让主人以为配好了却敲不响);保存时查重 |
| `enabled` | 开 | 关掉 = 整条入站链路只剩确认流 |

读取节奏分两种:**前缀与总开关每条消息现读**;**别名进了触发词表,要 `reconcile()` 重建**。重建挂在 `config-changed` 的 `globals` scope 上。

**前缀为空 ⇒ 未知指令静默(强制联动)。**前缀非空时 `/xxx` 意图明确,可以安全地回「没有这条指令」。一旦前缀为空,同一套逻辑会对主人**每一句聊天**回这句话。这两个开关在代码里绑死,不能只在 UI 上写行提示指望用户自己想明白 —— 用户配出一个会打扰自己的组合,是我们的设计错误,不是他的操作错误。前缀为空时行为退化为:整句精确匹配、认不出就当没看见。

**别名整份替换。** 配了就整份顶掉内置那份(`[]` = 一个别名都不要),没配过(键不在)才用内置的。面板上的「恢复默认」发的是显式 `null`(JSON Merge Patch 的删除哨兵),不是空数组 —— 两者是不同的意思,不能在线格式上合并。判定收在 `effectiveAliases` 一处,指令表与帮助共用;各写一份的话,帮助迟早会列出一批敲了没反应的别名。

**触发词冲突有两道防线**,共用同一个 `effectiveAliases`(各写一份的话,这边放行的配置到那边照样撞):

- **保存时** —— `checkCommandAliases` 拒绝并说清跟谁撞了(400)。用户给「周报」起别名「状态」,运行时只能二选一而且是静默的,他会看到一条指令神秘失灵;保存那一刻就拒绝。
- **构造 / 重建时** —— `compile` 再查一遍。查重按小写比(匹配本来就大小写不敏感,放过 `Mute`/`mute` 等于放进一对必然静默失灵的触发词),报错里印主人**写的那个**大小写。

两处抛不抛不一样,别改齐:**构造期抛**(这时候撞车只可能是代码里内置的几条自己撞了,是 bug,该在启动那一刻炸);**`reconcile()` 不抛**,保住上一份表 + 记 error —— 它在 `config-changed` 的总线回调里被调,抛出去就是一次 unhandledRejection,而独立端装了处理器会直接关掉进程。能走到那儿说明配置是从别的路径写进来的(恢复备份、手改盘上的 json),更不该拿整个服务陪葬。

**帮助文案全部动态渲染。** 不硬编码 `/静音 3h` 当示例 —— 用户把前缀改成 `bn ` 之后,帮助里每个例子都是错的,而帮助恰恰是他改完后第一个会看的东西。`spec.example` **只写参数部分**(如 `3h`),前缀与指令名由 `command-help.ts` 现场拼。面板卡片同理:照 `GET /api/commands` 渲染,不手写指令清单,`usage` 那一列还与私聊帮助共用 `renderUsage`(两处各写一份的话,同一条指令会在网页和私聊里印出不同的用法,而主人没法判断哪个才对)。

## 错误反馈分层

| 谁 | 情况 | 反应 |
|---|---|---|
| 非主人 | 任何输入 | **静默**。连「你没权限」都不回 |
| 主人 | 不带前缀的普通聊天 | 静默 |
| 主人 | 总开关已关 | 静默(他自己关的,不需要被提醒) |
| 主人 | 带前缀 + 未知指令 | 提示 + 最接近的触发词(前缀非空时) |
| 主人 | 带前缀 + 参数不合法 | 说清哪个参数错了 |
| 主人 | handler 抛错 | 记日志,不带塌这条入站链路 |

最能说明顺序意义的是第一行与第四行:同样是「未知指令」,主人收到提示,陌生人一个字都收不到。

### 近似建议

`suggestCommand(typed, triggers)` 在活的触发词表上做编辑距离匹配,返回**命中的触发词原样**(别名也算),由分发器拼上当前前缀发出去。三条判定:

- **只比第一个词。** 整串带参数去比的话,`/mut 3h` 离 `mute` 就有三步远,建议直接失灵。
- **预算 = `min(2, max(输入长, 候选长) - 1)`。** 减一保证短词必须几乎打对 —— 固定给 2 的话,`?` 这种单字触发词会被任意一个字母命中,主人随手敲个 `/a` 就被指去敲 `/?`;同时给 `help` / `status` 这类长词留出调序(`hepl`)这种双步手滑的余地。
- **拿不准就闭嘴。** 指错一条比不指更糟:主人会照着敲第二次,发现还是不对,才开始怀疑我们。

按**码点**切,不按 UTF-16 码元 —— 别名是主人自己填的,填个 emoji 完全可能,按码元切会把一个字拆成两半、算出虚高的距离。并列时取注册在前的那个,同一次手滑跑两遍不能给出两个答案。

建议敢在这里出声,是因为已经过了鉴权门 —— 它本质上是接口指纹,试探者拿它当探针几次就能把指令表摸出来。所以它只能长在 unknown 分支上,前提是「已确认是主人 + 带了前缀」。

## 命令即数据

注册表是**可序列化的声明**(`name` / `aliases` / `signature` / `description` / `details` / `example`),不是一堆散落的 if-else。由此白拿三件事:

- 帮助自动生成,**永不过期**(手写帮助必然与实现脱节)
- 面板的指令卡片能直接列出「你可以在私聊里用这些」,解决可发现性
- 测试能枚举全部指令做统一断言

## 边界

- **不做 flag/option**(`-c`):现有指令用不上,真需要时再长。
- **不做子命令树**:koishi 端有 `bili.xxx` 是因为它要和别的插件共享命名空间;独立端这条私聊只有我们一家,平铺就够。
- **不开群内指令**:现有指令没有一条适合群里用。一旦有指令在群里可用,群里就必然产生回音,试探面从「知道我 QQ 号的人」扩大到「同群所有人」。因此 `CommandSpec` 上**没有**权限级字段 —— 全部指令一律主人专属,由鉴权门一处判定;加一个当前恒为 `master` 的字段只会让人误以为它真的在管权限。
- **不做备份指令**:手机上收到备份也恢复不了,而它会把 B 站 cookie / 面板密码 / API keys 送进第三方服务器,是风险最高、离开电脑时又最用不上的一条。
