# ADR-0009:借 koishi / AstrBot 的机器人 —— 桥接的形态与协议

- **状态**:**协议、服务端与 koishi 插件都已实现,未发版、一次真机都没跑过**(2026-09-07 经 `/grill-me` 六轮拷问定案;服务端八片落 dev,协议 v1 见 `extensions/bridge/PROTOCOL.md`)。koishi 那侧的薄插件 2026-09-10 写完,**住它自己的仓**(决策 8),本仓里没有它一行代码。
- **记录方式**:⚠️ **事后追认** —— 据定案记录与已落地的实现整理,**非当时拷问的原文**。
- **影响面**:整块住 `extensions/bridge/`(2026-09-09 起,见 ADR-0012 决策 3;从前散在 `apps/contract/src/bridge.ts`、`apps/server/src/bridge/`、`apps/server/src/platforms/bridge.ts`、`docs/protocol/bridge.md`);数据模型那一侧见 ADR-0011
- **⚠️ 已被取代的部分**:本 ADR 原稿里的**数据模型**一节(`platform` → `{driver, platform?}`)**已作废** —— 主人 2026-09-08 撤回整套改名,由 ADR-0011 的新模型取代。**别再提议改名到 `driver`。** 桥接的**形态**与**协议**决定不受影响,全部仍然有效。
- **🔗 后续**:桥接本身将被搬出核心、成为第一个拓展,见 ADR-0012

## 背景

主人要「统一接口协议、把口开出来」连 koishi / AstrBot,桥接插件单独成仓、不污染主仓。

真正的动机不是「多支持两个框架」,而是**不必为每个聊天平台各写一份适配**:telegram、discord、kook 这些平台,koishi 和 AstrBot 早就有人写好适配器了。BN 要的只是**借用它们已经配好的 bot**。

## 决策

### 形态

1. **桥主动连 BN,不是 BN 连桥。** BN 开一个 `/bridge` 端点收桥;面板生成长期 token,插件那头填「BN 地址 + token」。重连退避归插件。先例是 OneBot 的 ws-reverse —— 那本来就是「BN 开口、bot 连进来」。
2. **专用端点、独立协议版本**,与 dashboard 那条 WS 彻底分开。那条的帧想改就改;而且现有凭据(cookie 与 30 秒一次性 ticket)桥都拿不了,本来就得新开一种。
3. **一桥一长期 token,多桥并存,可吊销**(吊销即断连)。握手报协议版本,**major 相同即接受**;BN 也把自己的版本告诉桥。
4. **桥在词表里只占一档 `bridge`**,是 koishi 还是 AstrBot 放 `config.bridgeKind`。推翻了最初「适配器增加 koishi 和 astrbot 两档」的说法 —— 两个桥说同一套协议、BN 侧处理完全相同,分两档就是两份几乎一样的 schema 分支,而且每来一个新桥都要改核心词表发一次版。

### 协议纪律(2026-09-08 落协议时新拍的三条)

5. **鉴权挪到 HTTP upgrade 的 `Authorization: Bearer`** —— 不在 `hello` 帧里、更不在 URL 里(URL 会进反向代理的访问日志)。
6. **未知帧类型忽略,已知帧畸形拒绝。** 所以「认不认识这个 type」必须判在 zod **之前** —— 判别联合分不出「对面比我新」和「对面在发垃圾」。两个方向对称,于是任一边都能单边演进。
7. **bot 名单是全量快照,不是增量。** 推翻了原设计的增量帧:两边都能轻松产出快照(轮询那侧更是如此),而增量要求两边对齐顺序与丢帧语义。

### 能力

8. **能力归桥声明,不是 BN 探测。** 调研过一轮:@全体 / 发图 / 合并转发这类能力是**消息元素**级的,而桥那一侧拿得到的自省接口是**方法**级的 —— 问不出来,试也试不准。所以只能由桥自己**声明**。
9. 决定性的理由是**能力是「桥 × 平台」的函数**,不是平台自己的属性:同一个平台经不同的桥连进来,能拿到的能力可能不同。**桥天然是一维表,BN 要建就是二维表** —— 而且各家桥报上来的平台名不保证同名,那张二维表的第一维我们根本对不齐。
10. **必报五项、每项三态**:@全体 / 能否收回复与指令 / 合并转发 / 小程序卡 / 分享卡链接 × `supported | unsupported | unknown`。**三态不是布尔** —— 桥对没见过的平台会真的不知道。桥可额外报别的键,BN 静默忽略。**发文本恒真,不做成能力项。** UI 上「不支持」与「还不知道」**要分开显示**。
    🔴 **三态靠形状分,颜色只是第二条通道**(2026-09-10 补):实心打勾 / 空心一横 / 虚线空圈,并且**记号旁必须有图例**。反面教材是真发生过的 —— 第一版拿**删除线**画「不支持」,而删除线在这套界面里说的是「作废 / 坏了」,于是一张完全正常的 onebot 能力表被读成了故障。同理:颜色单独不够用(色觉差异与截图压缩都吃得掉它),而两个空心圈不配图例就只能靠猜。
11. **能力挂在 bot 上,不是挂在连接上** —— 一条桥接入底下可能同时挂着 QQ 与 telegram。

### 收发

12. **双向**:出站推送 + 私聊指令 + 群链接解析全通。入站在 BN 侧几乎白拿 —— 形状与接线都现成。
13. **入站按需订阅**:BN 握手后下发一小组固定参数(私聊全要 + 群消息只要含链接的)。**群白名单不下放** —— 那是 BN 的策略、BN 本地过滤。
14. 🔴 **图走一次性取图口 `/bridge/blob/<id>`**:128 位随机 id 即凭据、短 TTL、取过即焚,不另挂 token。协议里必须写死一句:**这个 URL 只保证桥自己可达;桥要交给平台去拉必须自己先下载** —— 否则 NAS 上的 BN 遇上 Telegram 服务器拉不到,而且是**静默失败**(用户看到一条没有图的消息,日志里什么都没有)。
15. 便宜捡到了:桥那侧多半能直接吃一条 http URL,所以**桥与 BN 同机 / 同内网时,桥连一次内存拷贝都不用做**。

### 出事时

16. **桥断线 → 推送直接失败,不排队不补推。** 推送有时效,补推一条三小时前的「正在直播」比不推更糟。
17. **bot 消失 → 目标不删,只标不可用。** 用户配置不能被外部程序抹掉。
18. **模块关闭 → 断连 + 配置全留**,推送失败并显示「桥接模块已关闭」,重开即恢复。

### 界面与命名

19. 分工:**接入在拓展页建**(选桥类型、生成 token、看状态与 bot 名单与能力矩阵),**目标在推送目标页建**(选接入 → 选 bot → 填群号)。
20. 🔴 **配置里的桥种类与桥自报的种类对不上,要当成一个态说出来**(2026-09-10)。成因很具体:两条接入的 token 长得一模一样,填到另一头那个插件里去是最容易犯的错。而它**收发一切照常**(BN 对两种桥的处理完全相同),除了面板上的名字对不上没有任何别的症状 —— 不主动说就永远发现不了。所以:黄点 + 一句「连上了,但对不上」+ 一颗就地改过来的钮,同时**明说它其实能用**,免得主人跑去拆本来好好的配置。
21. **新建接入那一刻要把 BN 地址与 token 摆在一起,两样都能复制**,并且**屏幕上显示的必须就是存下去的那一把**。它们是一对,少一样连不上;而「显示一把、存另一把」的症状是插件收到 401 而面板一切正常。token 只在这一刻给全文,之后只留头尾。
22. **全线统一用 `bridge`**。主人问过为什么不叫 connector,三条理由:主人自己的原话就是「桥接插件」;connector 在英文里指「A 系统里连 B 的那个部件」,是单边的,而这东西是双向对等的两半;仓里已有 adapter,connector 跟它语感太近。
23. **拓展页照设计稿 V1 一比一画,差的补、多的去**(2026-09-10,主人拍板)。前两轮往旧骨架上贴 V1 的零件,骨架没换,主人两次说「差距还是大」;第三次整页重画:列表卡(头 / 一段描述 / 「N 条接入 · N 个 bot 在线」/ 管理 ›)、详情头卡(正文只有地址行)、接入卡作**页面级兄弟节点**、三态各一屏、新建弹窗。V1 里**不成立**的不搬:「模块随版本内置」「`/bridge` 地址」「机器人 / 数据源」分组、两个插件包名、「桥接模块已关闭」那个不存在的字符串。V1 **没有**的去掉:就地改名(代价认下 —— 改错名要删了重建、等于换 token)。V1 **有而数据没有**的补上:「来自 192.168.1.5」→ 会话记 `remoteAddress`;列表卡的 bot 数 → 列表页也读桥的状态口(仍是面板里唯一认得桥的那一处)。

## 明确不做(拷问中被否决的)

- **AI 借道桥接**(暂缓,别再当成「加一档 provider」):BN 的 AI 是**流式**的、**联网搜索完全建立在 function calling 上**(自家 `web_search` tool,不是各家原生方言),桥不透传 `tools`/`tool_calls`/`role:"tool"` 就整条断;另有五处硬校验拦「没 apiKey/baseUrl」的实例。最贴合的切面是 `apiFlavor` 加第三档,不用重造抽象。
- **BN 去连桥**:见决策 1。
- **koishi / astrbot 各占一档**:见决策 4。
- **增量 bot 名单**:见决策 7。

## 后果

- 协议契约住 `apps/contract`,于是那个包**同时驮着两条 wire**:server↔web 与 server↔桥插件。zod 校验是服务端的事,contract 只放纯类型与常量。
- 桥连接**没有 `platform`** —— 它后面挂着哪些平台是握手时报的运行时知识。这条直接催生了 ADR-0011 里 `kind` 那根正交轴。
- **能力那张两级表(连接 × 平台)粒度不够** —— 协议一开始就是 per-bot,而 BN 内部的 `connectionCapabilities(id)` 与契约的 `ConnectionCapabilitiesMap` 都是 per-connection。这一格**至今没扩**,现状是桥的 adapter **刻意不实现 `capabilities`**(跨 bot 合并出来的答案对谁都不对)。代价:桥后面的群进不了面板上「逐群例外」那张选择器。

### 插件那一侧

8. **薄插件单独成仓,本仓一行都不放。** koishi 那侧是 `koishi-plugin-bilibili-notify-bridge`(2026-09-10 写完):它按平台**硬编**一张能力表报上来 —— 而且**只报查过的**(去翻那个平台适配器的消息编码器),拿不准的一律 `unknown`。谎报 `supported` 的代价不对称:症状是「@全体没生效而且一声不响」。
    做不到的一律**降级不丢弃**(合并转发→一张张发、小程序卡→标题+简介+网页链接),并且**每一条失败都变成一句回执** —— 不回的话 BN 只能等到超时,而那 30 秒里主人看到的是「推送卡着不动」。
    ⚠️ 那一侧**没有自动守卫**能发现协议漂了(插件跑不起一台 BN)。协议给的兜底是 `major` 对不上 BN 直接断连 4002 —— 所以漂了的症状是「连不上并给了个明确的码」,不是「连上了但行为诡异」。

## 仍未决 / 未验

- 🔴 **一次真机都没跑过**。插件写完了(单测绿、构建通过),但从来没有真的连上一台 BN 推过一条消息 —— 真框架的怪癖只有真机验得了。验的时候**先用 devtools 的假桥单独跑一遍 BN 那半**(ADR-0012 决策 42),不然出了问题分不清是哪一侧。
- 能力扩到 **per-bot** 还没做。
- 入站帧与回复目的地都**没有 `parentAddress`** —— Telegram 论坛话题的链接卡会回到主群而不是那个话题。补它要给协议加一个可选字段(minor 就够)。
- 「模拟一条桥接入」**做了**:devtools 的「假装一条桥连上来」+「桥驮一条消息上来」(2026-09-10,见 ADR-0012 决策 42)。于是上面那条「一次真机都没跑过」里,**拓展页、能力矩阵、状态面板、失败提示、入站**都不必等插件写完就看得到;真插件那侧的怪癖仍然只有真插件验得了。
