# ADR-0020：统计也管拓展订阅 —— 采、存、算、评四段都按「谁」认人

- **状态**：2026-09-24 拷问定案（五题）；未动工
- **记录方式**：拷问当场落的定案，不是追认
- **影响面**：`apps/server` 的统计采集、统计仓与粉丝仓、粉丝轮询（只动停用那一条）、统计与锐评的路由、锐评的生成 / 投递 / 定时、拓展直播的计时器（场次抽出来共用）；`packages/internal`（拓展订阅多一格 `roastSchedule`、拓展配色的种子搬进来）；`packages/ai`（人格那一句）；`packages/image`（锐评卡的头像）；`apps/contract`（统计行与锐评结果的身份）；`apps/web` 的统计页与首页粉丝面板
- **依赖**：[ADR-0019](0019-subscription-source-opening.md) —— 本份细化它的决策 63（统计进第一版），并沿用它的决策 73（历史的身份）、69（拓展作品套 B 站类型）、75（人数两格）、58（断流接续）、53（不拿状态猜开播 / 下播）、62（停用的订阅照收资料）、64（粉丝轮询是 B 站独有）、65（中立指结构、不改名）

## 背景

ADR-0019 决策 63 定了统计页、粉丝曲线、锐评三样都管拓展订阅，并留下四处语义「到那一步再逐题拍」。0019 已经很胖、主题还没收尾，而统计这一摊自成一条链（采集 → 存储 → 统计页 → 锐评），读它只需要引用 0019 的几条，所以按 README 的规矩另开这一份。

动工前查实的几件事：

1. **全链以 B 站 uid 为键**：采集只听 B 站引擎发的三条事件（动态被侦测到、直播间人数、开播 / 下播）；盘上是每位 UP 一个以 uid 命名的文件；发给面板的行以 uid 为身份；锐评的请求、草稿、定时也都按 uid。拦住拓展订阅的入口约十五处。拓展的五种上报一种都进不了统计。
2. **「投稿」今天只认视频**（B 站的 `DYNAMIC_TYPE_AV`）；开播那两种剔掉（场次另记）；转发、图文、纯文字、专栏、合集都算「动态」。
3. **「峰值」那一列存的是直播间「X 人看过」**，即本场**累计**观看，只增不减 —— 所谓峰值就是本场最后那个累计数，列名「峰值观看 / 场均峰值」名不副实。
4. **粉丝曲线只来自 BN 自己轮询 B 站**；统计页判「那天有没有记录」也全靠粉丝采样（所有 UP 采样日的并集证明 BN 在跑，每位 UP 的首个采样日遮掉它之前的 0）。拓展行照原样接进来，④′ 上线之前那些天会被画成**假的 0**；只订了拓展、B 站没登录时又整片「无记录」。
5. **锐评写死了平台**：提示词是「我订阅的 N 位 B 站 UP 主」，人格核心那一句「帮用户关注 B 站 UP 主」所有 AI 调用都带着；单人定时锐评那一格只长在 B 站订阅上；拓展头像是面板里的相对地址，出卡截图时加载不到；拓展的配色算法只在面板里有一份。
6. **B 站直播只有直播间在监听时才记场次**（至少开了一个直播类推送）—— 这是听一个直播间要占一条连接逼出来的，不是有意的口径。拓展的直播上报不管推送开没开都会来，但拓展直播的计时器在开播、下播推送都关时会把这一场扔掉。
7. **老漏洞**：停用一个 B 站订阅，它的粉丝时序文件会被删掉。那段清理的本意只是让停用的 UP 从首页粉丝面板上撤下来，而统计页照样列着他、曲线却清空了。

## 决策

### 身份与存储

1. **统计行的身份照 ADR-0019 决策 73**：B 站认 uid，拓展认「拓展 id + 外部 id」。发给面板的行与锐评结果带这两支（同推送历史），面板按它们选中、配色、做键。
2. **拓展的统计与粉丝文件按订阅 id 命名**。外部 id 是平台给的不透明串（可能带 `/`、最长 256 字、大小写不敏感的盘上会撞名），当不了文件名；而统计本来就随订阅一起删，按订阅 id 命名一点不丢。**B 站的文件不迁移**，老数据原地不动。
3. **名字**走卡片与历史那同一条链（0019 决策 77，少了事件里的作者名）：资料里的名字 → 主人起的别名 → 外部 id。单人页头 B 站写 UID，拓展写平台名 + 外部 id。

### 采集

4. **拓展订阅启用着就记，与推送开关无关**。统计记的是「UP 做了什么」，与推送推没推无关（0019 决策 63）。停用的不记，与 B 站同一个口径 —— 哪怕它的资料照收（0019 决策 62）。
5. **作品**按（订阅，作品 id）去重，按发布时刻记到哪一天。**投稿 = 带视频的作品**（套进 B 站类型之后的 AV，0019 决策 69），图文与纯文字算动态。「投稿 = 发了视频」跨平台同义，榜单把抖音与 B 站放一起比时比的是同一件事。
6. **直播场次的边界按这位 UP 的断流接续合并**（0019 决策 58），与 B 站同一个口径。「这一场从哪开始、到哪结束（含断流等待）」从拓展直播的推送计时器里**抽出来，统计与推送共用一份** —— 各算各的迟早对不上。
   - 开播时刻取开播事件的；BN 起来后先收到在播状态的，取状态里带的开播时刻，没带就取收到的那一刻。下播仍只由事件触发（0019 决策 53）。
   - 拓展停了：补一帧下播（与 B 站停止监听那一路同口径）。BN 或拓展重启之后按开播时刻接回同一场（同 B 站按开播时刻认场次）。BN 关服时一并补下播。
7. **峰值 = 本场累计观看**：B 站取「看过」那个数，拓展取 `totalViewers`；平台只报此刻在线、不报累计的，这一场的数空着，**不拿在线人数顶替**。存成数字。

### 粉丝

8. **拓展的粉丝时序来自资料上报里带的粉丝数**，契约不加方法（粉丝轮询仍是 B 站独有，0019 决策 64）。报得太密的合并，不密过 B 站那边的采样间隔。平台不报粉丝数的，粉丝那几格空着，其余照常。首页粉丝面板（起点 / 24h / 7d）也列出有粉丝时序的拓展订阅。
9. **「那天有记录」各算各的**：拓展行看它自己的上报（资料、直播状态、作品），开始记录之前的日子一律「无记录」，不画 0。B 站行的规矩不变。
10. **停用不再删粉丝时序**（修上面第 7 条老漏洞）：停用只把他从首页面板的快照里拿掉，文件留着；删订阅才删文件。拓展从一开始就照这个规矩。

### 统计页

11. **列名改诚实**：「峰值观看 / 场均峰值」改成「单场最高观看 / 场均观看」，旁边一句「按每场累计看过的人数算」；CSV 表头跟着改。

### 锐评

12. **一张榜混着比**：提示词去掉「B 站」、保留「UP 主」（0019 决策 65：中立指结构，不改名），数据表多一列「平台」。锐评评的是勤不勤、鸽不鸽，本来就跨平台可比；平台那一列让女仆不拿抖音的粉丝量去压 B 站的。
13. **人格核心那一句**改成「帮用户关注 B 站等平台上的 UP 主」：B 站的语境还在，也不把别的平台排除在外。
14. **单人定时锐评长到拓展订阅上**（拓展订阅多一格 `roastSchedule`），审批闸照 B 站那样。
15. **锐评卡**：拓展头像出卡前转成内嵌图（与 0019 决策 68 同一个坑）；拓展的配色种子搬进 `packages/internal`，面板与出卡用同一个算法。

## 明确不做

- **拓展作品一律算投稿**（「平台的单位就是作品」）：只发图文的号会在投稿上压过 B 站的视频 UP，跨平台就不可比了。
- **只报在线人数的平台拿在线人数的最大值当峰值**：「看过的人数」与「同时在线的人数」差得很远，同一列混两种意思，还不如空着。
- **峰值列名不改**：名不副实留着，拓展行也跟着错。
- **拓展只显示当前粉丝数、不画曲线**：0019 决策 63 答应的是曲线也管，只进一半比整行没有更怪。
- **契约加一个「BN 定时问拓展要粉丝数」的方法**：拓展本来就按平台的节奏报资料，照单记录就够；粉丝轮询是 B 站独有（0019 决策 64）。
- **按平台各出一张榜**：推送翻倍，每个平台都得至少订两位才评得出来。**拓展只进单人锐评、不进榜单**：榜单缺一半的人。
- **推送关着就不记拓展的直播**（照抄 B 站）：B 站那条是监听成本逼出来的，拓展没有这个成本。
- **按原始上报切场次、不合并断流**：断流一次就裂成两场，场次数与时长跟 B 站不是一个口径。
- **把 B 站的统计文件也迁成按订阅 id 命名**：老数据原地不动更稳，降级回旧版也读得回来。

## 后果

- 统计链约十五处入口要改；发给面板的行从「uid 必填」改成两支（同推送历史），面板按 uid 做的键、选中、配色全部跟着改。
- 盘上两种键并存：B 站按 uid、拓展按订阅 id，读写按支分开。
- 场次抽成共用的一份之后，拓展直播的推送计时器改吃它 —— 对推送是纯重构，既有测试全程保持绿。
- **两边的直播口径有意不对称**：B 站关了直播类推送就没有场次（监听成本），拓展照记。
- 拓展行的粉丝曲线疏密取决于拓展报资料的频率；不报粉丝数、不报累计观看的平台，那几格恒空。
- 人格那一句的改动影响所有 AI 调用（措辞放宽，不删 B 站）。
- 停用的 B 站订阅从此保留粉丝时序（从前会被删掉）。
