# ADR-0016：推送的「附加项」—— @全体 与下播的词云 / 总结是同一种东西

- **状态**：2026-09-19 拷问五轮定案；片① (统一成 `extras`)、片② (推送层按目标收窄) 已落地，片③ (面板) 未开工
- **记录方式**：拷问当场落的定案,不是追认
- **影响面**：`packages/internal` 的订阅 schema 与特性表、`packages/push` 的路由收窄、`apps/server` 的推送类型映射、`apps/web` 的 UP 抽屉。**`packages/live` 不动**（见决策 6）
- **依赖**：ADR-0011(推送数据模型)—— 同一片地,但 0011 没记过附加项的形状,只在改名那条里提过 `platformSupportsAtAll`
- **冲突**：与 2026-09-05 那轮拷问的「下播附加项无自己的路由」**直接冲突**,本份推翻它。那条定案不在任何 ADR 里(只活在工作记录与 0.10.0 的 CHANGELOG 里),所以没有旧 ADR 可标「被取代」

## 背景

0.10.0 之前,弹幕词云与 AI 总结各是一个特性,各有开关与推送目标 —— 做得到「这个群只发词云、那个群只发总结」。0.10.0 的推送模型重构把它们并成下播的两个附加项,共用下播的开关与目标,升级时三份目标取并集。有用户报告用的正是被砍掉的那一种:部分群不发、部分只发一种、部分两种。

拷问中查实的四件事决定了这份定案的形状:

1. **@全体 早就是按目标存的**(`atAll.<scope>[targetId]` 三态,没这个 key 就继承 `atAllDefaults`,schema 用 refine 强制 key ⊆ `routing[feature]`)。而 09-05 那条定案恰恰说附加项「像开播 @全体 那样」—— 结果 @全体 拿到了按目标的粒度,词云 / 总结没有。**不一致是当时漏的,不是有意的。**
2. **@全体 在发送上也是一条独立消息**(单独的 payload,落历史时 `role: "extra"`,排在本体那次回调之后),不是主消息的修饰。所以它与词云 / 总结**结构同类**,不是看着像。
3. **引擎只看总开关**:`isSubscribed` 一句 `return sub[type]`,当年按目标拦的 `hasTargets` 已删。渲不渲、开不开 WS、攒不攒弹幕由总开关定;发不发、发给谁由推送路由定。下播本身就是这么办的 —— 没目标照渲,推送层落一行「无目标」。
4. **老配置救不回来**:0.10.0 迁移取并集那一刻,「哪个群原来只订了词云」这个信息就没了。受影响的人得手动重配。

## 决策

### 模型

1. **「附加项」升成一等概念,四个键一视同仁**:`atAllDynamic`、`atAllLive`、`wordcloud`、`liveSummary`。**键是一维的** —— 每个键自己声明挂在哪个主特性下、标签是什么、默认值多少。走二维(`extras[附加项][主特性]`)的话,@全体 那两处默认值本来就不同(开播 ON、动态 OFF),还得再开一层「同一个键在不同特性下默认不同」。

2. **三层配置,四个键同构**:

   | 层 | 住哪 | 形状 |
   |---|---|---|
   | 全局默认 | 全局特性表 | `Record<ExtraKey, boolean>` |
   | per-UP 覆盖 | 订阅的 features 覆盖 | 同上的 partial |
   | per-目标 | 订阅上 | `Record<ExtraKey, Record<目标 id, boolean>>`,**三态**:没这个 key = 继承上一层 |

   统一之后 `atAll` / `atAllDefaults` 这两个名字从数据里消失。`atAllDefaults` 是 per-UP 的值,迁进 per-UP 覆盖层是 1:1 的;全局那层给出厂值(开播 ON、动态 OFF,照今天的约定)。**词云 / 总结原有的全局层不能丢** —— 「我所有 UP 都不要 AI 总结」现在一次就能设。

3. **附加项的目标必须是主特性目标的子集**:能收附加项的,必须先收得到本体。schema 用 refine 强制 key ⊆ `routing[主特性]`,与 @全体 今天的约束同一条。

4. **每档自己声明发送规矩**,写进注册表当数据,不散在代码里:排在本体前还是后、等不等它(await)、有没有平台限制。@全体 是「本体前、不 await、平台不支持就关」,词云 / 总结是「本体后、要等算完、无平台限制」。

### 运行时

5. **收窄在推送层**:推送类型映射到主特性的那一步旁边,再产出「这是哪个附加项」塞进广播选项;推送层取完主特性的目标列表后按那张三态表筛一道。routing 查找全仓只有一处,这样它仍然只有一处。

6. **引擎不看目标**(沿用背景 3 那条口径):词云照渲、AI 照问,发不发是推送层的事。`packages/live` 因此一个字不用动。

7. **收窄成空不算「无目标」**:主特性有目标、只是这个附加项没路由给任何人,是配置意图不是故障 —— 不落行、不弹卡、不记失败。本体那一行本来就在且是「已送达」。

### 面板

8. **维持「自定义」那道门**:要调某个目标的附加项,先把那个目标从「跟随订阅项」拨到「自定义」。四个附加项规矩完全一致,零新增 UI。切过去的代价是该目标的路由被冻结成订阅当前生效的那几项,从此不再跟随特性变化 —— 而用户此时本来就在说「这个群跟别的群不一样」,「自定义」是准确的描述。

9. **历史行安静地少一条**:被收窄掉的目标,那一行就是比别人少一条消息,不解释为什么。

10. **词表**:代码里 `extras` / `ExtraKey` / 注册表;面板统称**「附加项」**。`extra` 已经是数据层在用的词(历史行的 `role`),面板文案两处也在说「附加」。

### 节奏

11. **分三片**:① 统一 `atAll` → `extras`(**纯重构,行为一个字节不变**,既有测试保绿 + 补迁移测试);② 加两个新键、推送层按注册表收窄;③ 面板那三个子开关。第 ① 片一绿就证明搬家没打破任何东西,后面两片出问题时排查范围只剩新加的那点。

## 明确不做

- **目标级偏好**(「这个群永远不收词云」跨所有 UP)。目标从来只住在订阅的 routing 里,@全体 的按目标覆写也挂在订阅上;开这一档等于在推送目标上新开一根「推送偏好」轴,是另一个模型。per-UP × per-目标 能表达它的全部意图,只是要逐个 UP 点。
- **附加项单发**(不收下播卡也能收词云,即 0.9.x 的表达力)。放开会把「一行 = 一次推送 × 一个目标」的行模型拆掉:附加项又变回独立推送,四态里的「部分失败(本体到了、附加没到)」随之失去意义。
- **两个附加项捆成一把开关**。用户要的就是「只发一种」,而且订阅那一层本来就是两个独立布尔,到目标这一层捆起来前后不一致。
- **把周期「正在直播」一并纳入**。它跟开播共用目标的理由跟这里不同(同一张卡的复推,不是追加消息),而且没有人报过需求。为没人要的场景提前抽象,抽出来的形状多半是错的。
- **把发送时序也统一**。@全体 不 await 是修过的 bug(无管理权限的群发 @全体 会被协议端拒绝并重试,顺序 await 会把卡片正文连同后续任务一起拖住);抹平就把它引回来了。统一的是配置模型,不是时序。
- **让引擎提前知道「还有没有人收」从而跳过计算**。要把按目标的知识漏进引擎包,换的是一个用户自己就能避免的配置(全关了就该去关总开关)。
- **跟随态直接调附加项**。要能调就必须在跟随态**显示**已有覆写,否则会存下一条面板上看不见的设置 ——「我明明关了词云怎么还发」比多点一下开关糟得多;而要显示就得给跟随态的行新开一块 UI,改动比整个功能还大。
- **让 per-目标的 ON 越过该附加项的总开关**。折叠默认(全局 + per-UP)关着时,某个目标显式打开也不会收到 —— 引擎根本没去算。这跟「目标挂在 `routing.liveEnd` 上、但下播总开关关着就收不到下播卡」是同一条规矩,只是下沉了一层:总开关管引擎,目标管推不推,目标越不过总开关。要让那个群收到,就把该 UP(或全局)那一项打开,再把不想要的群关掉。
- **历史行解释「为什么没发」**。撑开这个口子之后,总开关关着的、免扰挡掉的、平台不支持 @全体 的都得标一句,那一行会变成一张解释清单。

## 后果

- **要迁已发版的数据**:`atAll` / `atAllDefaults` 从 v0.10.0 就在盘上。schema 层 preprocess,备份恢复一并走。代价是一次性的;而两份形状并存的代价是永久的,将来加第三个附加项还得再抄一遍。
- **@全体 白拿一个全局默认**(今天只有订阅级),是顺带的能力增长,不是负担。
- **一个认下的边缘浪费**:把某个附加项的所有目标都关掉却留着总开关时,那次 AI 调用照花钱、结果没人看见也不落行。判据是原则一致优先 —— 那种配置该去关总开关。面板可以提示一句,那是文案不是架构。
- **受影响的用户要手动重配**:0.10.0 的并集迁移已经把原始配置抹掉了,这份定案落地也复原不了。
- 附加项从此有了统一的注册表,「加一个附加项」变成往表里加一行 + 决定它挂哪、排本体前后、等不等。

## 仍未决

- **跨 UP 的目标级偏好是不是真需求**。报告人只说了「部分群聊」,没说是不是跨 UP;这一点得问他。若答案是「跨」,per-UP × per-目标 仍能表达,只是要逐个 UP 设 —— 到那时再判要不要开另一根轴。
