- **同批三份**：[ADR-0021](0021-neutral-core.md) 讲中立核心，本份讲数据代与迁移，[ADR-0023](0023-neutral-naming.md) 讲命名与改名。
- **依赖**：

  - [ADR-0001](0001-backup-pin.md)：备份信封。

## 背景

1.0 要改的盘上数据，比以往任何一版都多，涉及订阅、设置、历史、统计、皮肤、图片。有三条事实限制了能怎么改：

- **桌面壳和 boot.mjs 是冻住的**：它们不随应用内更新替换，所以载荷目录只能在 `<dataDir>/versions`，桌面壳 30 秒没就绪就杀进程、连续 3 次就把这一版判死。
- **自愈会无条件退回镜像自带的版本**：1.0 起不来，就会跑回 0.12，0.12 必须还能读自己的数据。
- **用户会主动回退**：已经发出去的 0.x 之间回退就会报错，这个问题修不了，但 1.0 往后不能再犯。

原稿里对这些情况有三套各管一段的写法：「1.0 写新目录」「迁移前备份，数据比程序新就先还原」「全新开始把数据挪到一边」。三套写法就意味着三套崩溃恢复要写、要测。

## 决策

### 数据代

1. **数据收成「数据代」（Q46）**：
   - 每次改数据格式的升级，在 dataDir 下开新的一代，旧代原样留着，本身就是备份；
   - 开机时选「schema ≤ 我」的最新一代，所以回退旧版不需要还原这一步；
   - 复用应用内更新现成的版本目录、比版本、保留规则；
   - 0.x 留在根目录的文件就是第 0 代，一个不改。

   **宿主件不分代**：`versions/`（里面有 `boot-state.json`、`manifest-freshness.json`）和 `logs/` 留在根目录。冻住的 boot.mjs 从 dataDir 推算 `versions/` 的位置，冻住的桌面壳把 `logs/` 写死了。**跨代共享的东西一律冻结格式**，日志行格式因此不改。

   理由：三套写法收成一种机制，崩溃恢复只写一套。
2. **先 listen 再迁移（Q47）**：
   - 开机先起 HTTP，健康检查立刻返回，这次开机就算成功；
   - 然后在同一个进程里把整代迁完，迁完才启动引擎；
   - 迁移期间面板显示搬家进度，不推送（修正 Q32 的「迁移时照常推」）；
   - 新代先写成 `.partial`，完成后原子改名；中途被杀，下次开机删掉半截重来。

   理由：只要迁移挡在 listen 前面，桌面壳 30 秒没就绪就会杀进程，连续 3 次就把 1.0 判死，退回 0.12，而且用户看不到任何提示。

   被否的备选：分两段迁移，小文件先迁，大块内容 listen 之后接着跑。它会让同一个文件两头同时写，要专门写合并逻辑，还会出现一段「数据不全」的状态。

   🔗 **2026-09-30**：「这次开机就算成功」指桌面壳的判定。健康检查在 listen 之后马上回 200，但载荷的启动入口要等迁移与引擎都起来才返回；迁移或起引擎抛错时先关掉 HTTP 再抛出去，冻住的 boot.mjs 照旧当场退回预装的那一版，0.x 读自己没动过的旧文件，自愈不受影响。
   🔗 现状（4-19，2026-10-30）：先 listen 的开机 app 现在也答 `/api/health/details`，交 `migrating` / `starting` 阶段与 `{ step, total, label }` 进度（首个回调前为 null）；完整 app 接管后交 `running` 与运行详情。只读现有迁移回调，不改迁移产出、修订号或备份版本。详情沿用鉴权，短版仍严格四格；面板全屏搬家闸归 4-41。
3. **回退后再升级：谁最后在用，就以谁为准（Q48）**：
   - 每一代记下自己最后活跃的时间；
   - 0.x 的根目录没法改代码，就在迁移时记下关键文件的修改时间与大小，当作指纹；
   - 开机时发现旧代在新代之后又被用过，就从旧代重新迁一遍，开出新的一代；被替下来的那一代挪到一边，不删；
   - 新版在回退之前产生的那段数据不带过来，面板上说清楚；cookie 与订阅会随之跟回来。

   被否的备选：把两代的数据合并，订阅、历史、统计要各写一套合并规则，还有两边都改过同一份数据的冲突。

   🔗 **2026-09-30**：代目录按递增序号放在 `<dataDir>/generations/<序号>/`，写到一半的叫 `<序号>.partial/`。开新代（首次迁移、回退后重迁、全新开始）一律拿下一个号，旧代原地不动、永不改名；格式版本、从哪一代迁来、最后活跃时间都记在代里的 `generation.json`，选代就是在「格式版本 ≤ 我」的代里取序号最大的。上面那句「被替下来的那一代挪到一边」因此不需要了：它本来就留在原地。
   理由：只剩「开新代」一种动作，没有改名这一步，崩溃恢复只写一套。按格式版本起名（一个格式一个目录）的话，回退后重迁、全新开始都会撞名，每次都得先把旧的改名挪开。

   🔗 **2026-09-30**：开发期重迁。1.0 开发期每一期都在改盘上格式，格式版本却一直是 1，迁出来的那一代会跟着代码变旧。每一代再记一个迁移修订号，开发期每改一次迁移的产出就加 1、只比一样不一样；对不上就照当初的来源重开一代，和回退重迁同一条路，代价是开发期在新代里产生的数据带不过来。修订号在 alpha.1 冻住。
   被否的备选：每一期写「上一版开发代 → 这一版」的迁移（开发期的每个中间形状都要各写迁移、各配测试，发出去以后全是死代码）；开发期由主人手动删代目录重迁。

   🔗 **2026-10-01**（⑦ 拷问，主人拍板）：改成**只迁一次，之后各代互不干涉**。新版只认格式版本与自己对得上的那一代，盘上有就直接用，没有才从能迁的旧代迁；回退到旧版，旧版用它自己那一代（0.x 读第 0 代），新版在回退前产生的数据不带过去；再升回来，新版照用自己那一代，回退期间旧版产生的数据留在旧代。要以旧代为准，由主人在系统页点「从旧代重新迁移」：开下一个号的新代，当前代原地留着当备份，和全新开始同一条路（决策 5）。`lastActiveAt` 只给系统页显示「最后使用时间」，不再拿来判谁最后在用；第 0 代的指纹不做。新版起不来、被自愈退回时，面板据启动器现有的判死名单（`boot-state.json` 的 `failed`）说「X 起不来，已退回 Y」；退回的目标是 0.x 时说不出来，0.x 的面板改不了。启动器不另记开机史。
   理由：自动判谁最后在用，就得给第 0 代记指纹、开机比对。全量记的话每次开机要 lstat 上千个文件，误判一次就把当前代扔掉；只看设置与密钥又会漏判。互不干涉没有误判这回事，代价写进后果；自愈那种主人不知情的回退，有判死名单的提示加手动重迁兜着。
   被否的备选：只提示、不动手的小指纹（只记 `state/`、`secrets/`）；启动器另记开机史，升回来时说明中间跑的是哪一版。两者都只是事后告知；后者只覆盖重新下载了新启动器的人，而最容易碰上静默自愈的应用内升级用户，用的仍是旧启动器。

### 迁移

4. **一次性迁移模块（Q30、Q34）**：
   - 旧格式的知识只住在迁移模块里，新 schema 不留兼容分支；
   - 第 0 步收编 0.x 现有的兼容代码，所以输入可以是任意 0.x 版本；
   - 除卡片皮肤外全部迁过去；AI 对话里对皮肤的引用剥掉，文字保留；
   - 老测试夹具搬成迁移模块的夹具；
   - 加一条迁移耗时测试，用 365 天的合成数据跑。

   🔗 **2026-10-02**（⑨，主人拍板）：判据是「增长比 + 宽上限 + 照实打印」—— 满量（重度用户把 0.x 用满一年：40 + 4 个订阅、历史留满 365 天）与四分之一量（订阅 10 + 1、历史 91 天，每一块会涨的东西都严格 1/4）各迁一遍，满量 ÷ 四分之一量 ≤ 5.5（与机器快慢无关，专抓越积越慢的步骤；干净比值约 4.05，上限 5 余量太窄、CI 抖一下会误红），满量 ≤ 5 分钟（只拦卡死），两档的秒数打出来回答「推送要停多久」。默认的测试不跑它（要设 `BN_MIGRATION_TIMING=1`），本地用 `vpr test:migration-timing`，CI 另开一个与门禁并行的作业，每次推送都跑，发版门禁不变慢。

   🔗 **2026-10-01**（⑥c 收密钥那一族时主人拍板）：`globals.json` 里出现明文 apiKey 就抬进加密袋、抹掉盘上那份，这一步**不算 0.x 兼容**，是一直成立的规矩「盘上不留明文」，留在配置仓 —— 主人手改写进去的 key 不抬的话，下次保存被抹掉、袋里又没有，重启就悄悄丢了。与袋里同一格冲突时**明文优先**：每次抬完盘上都会抹掉，盘上的明文只可能是之后写进去的。加密袋里 0.x 单把的 `aiApiKey` 才是兼容，进迁移器。
   🔗 **2026-10-14**（3b-53，主人定；落细处主会话照规矩定）：**0.x 的女仆技能与女仆对话不迁，修订上面「除卡片皮肤外全部迁过去」的范围**。0.x 升 1.0 时 `maid-skills/` 与女仆对话都不带进新代；AI 设置（连接、密钥、人格）照迁。它们留在第 0 代，不自动删，当前代满 30 天后主人可以手动清（决策 7）。会话的迁移与聊天附件进图库那一步撤掉，随之「AI 对话里对皮肤的引用剥掉」这一句对女仆对话也不再有对象。内置技能改名后旧斜杠名的别名见 ADR-0030 决策 1 下的 🔗。

5. **开机自动迁移，首次打开面板时问要不要全新开始（Q32、Q33、Q49）**：
   - 询问页说明旧数据还在；
   - 全新开始 = 开一个空代，回到新手引导，B 站重新扫码，token 与 AI key 重新填写；
   - **全新开始不碰 `bn.config.yaml` 与环境变量**，面板账号保留。

   理由：面板账号只在 bootstrap 配置或环境变量里。清掉的话，监听 0.0.0.0 的 Docker 会拒绝启动；环境变量里的账号根本清不掉。

   被否的备选：用环境变量来控制迁移。自动更新的 Docker 不会有人去设这个变量。
6. **1.0 之前的备份不收（Q31）**：备份信封改成比自己新、比自己旧的都拒收，提示「先装 0.12 恢复，再升级到 1.0 走迁移」。
   🔗 **2026-10-01**：从 ⑧ 提前到 ⑥d 落地。订阅合成一节以后，老备份里拓展订阅那一节没人认；B 站那节是空的时候，「覆盖」模式会把现有订阅全删光、不报错，所以拒收要赶在订阅合一之前。备份格式版本抬到 2；恢复路径上的 0.x 形状迁移随之删掉；完整档的加密袋只留 cookie 与照脱敏结果现算的那一份，从前另抄 apiKey 与连接 config 是为了旧版本也打得开新备份，旧版本见了版本 2 就拒，那两格没用了。
7. **旧代不自动删（Q59）**：
   - 当前代永远保留；上一代默认保留，迁移满 30 天才允许清理；更早的代列为可清理；
   - 系统页的「旧版本数据」显示每一代的版本、最后使用时间、大小，以及清理按钮；确认框写明清掉以后就回退不到那个版本；
   - 第 0 代按写死的白名单清理，`versions/`、`logs/` 永远不碰；
   - ~~迁移时任何链接失败都回落成复制；追加写的 jsonl 一律复制，不做硬链接，否则新版往里追加时会改到旧代的文件。~~ **迁移一律复制，不硬链接**（见下面第二条 🔗）。

   理由：旧代就是备份，删备份得主人点头。

### 代内布局

   🔗 **2026-10-06**（㉙ 开片拷问，主人拍板）：「上一代锁 30 天、更早的可清」改成**按来源保护**。字面规则按序号算，但「重新迁移」是从第 0 代再迁一份（0 → 1 → 2，第 2 代的来源是第 0 代），按序号第 0 代成了「更早的」、立刻可清，而它是 0.x 数据的唯一一份、当前代的来源、再次重迁与退回 0.x 时要读的东西，删了回退会被当成全新安装。现在的规则：当前代永远不许删；当前代的**来源代**与**上一代**都要等当前代用满 30 天；写到一半的与格式版本比我新的不许删；其余可清。服务端自己判断、不能删就拒绝，不靠面板藏按钮。删除不可恢复。接口 `/api/system/generations`。施工时补的两条：30 天从当前代 `generation.json` 的 `createdAt` 算（不用每次开机都刷新的 `lastActiveAt`），读不到就全部锁着；`generation.json` 读不懂的代不许删（可能是更新版本写的），代价是真坏掉的只能手动清盘。被否的备选：第 0 代永远单列（满 30 天后其实已可放心删）；照字面不改。

   🔗 **2026-10-06**（1.0 代码审查后，主人拍板）：**迁移搬文件一律复制，硬链接这条路整个撤掉。** 原来的写法是「追加写的 jsonl 复制，其余硬链接」，靠文件后缀判断；硬链接是新旧两代共用盘上同一个文件，哪边原地写都会改到另一边。1.0 自己全是「写临时文件再改名」，改不到旧代；但回退到 0.x 以后，0.x 原地写的那几类（女仆对话、字体清单、封面轮换游标、登录 cookie、界面皮肤的素材、重推原件）会改到新代里的同一个文件。能不能链取决于新旧两边的写法，而旧版本的写法已经发出去、管不了。和决策 9 下「迁移把老图复制进图库」是同一个道理往旧版本那头补齐。代价：字体、封面图、拓展这几类多占一份盘，旧代清掉后还回来。被否的备选：默认复制、只给点名的几类写一次就不改的文件留硬链接（要逐类维护名单，字体目录还是混的，判错一类又是同一个问题）。迁移修订号抬到 35。
8. **代内怎么排（Q60）**：
   - **小状态按性质分**：`config/` 放主人填的；`secrets/` 放密钥；`runtime/` 放程序自己记的，丢了只会退化。
   - **小状态的第二层按归属分**：内置 B 站用 `bilibili/`，拓展用 `extensions/<id>/`。不设 `sources/` 这一层，因为内置来源只会有 B 站一个。拓展 id 就算也叫 `bilibili`，落在 `extensions/` 下面，也撞不上。
   - **大块内容按领域分**：`history/`、`stats/`、`ai/`、`skins/`、`library/`、`images/`、`maid-skills/`、`extensions/`（已装的拓展包，跟着代走，回退时拿回旧版拓展）。
   - **来源的运行状态**（ADR-0021 决策 39）落在 `runtime/bilibili/state.json`、`runtime/extensions/<id>/state.json`；凭据落在 `secrets/bilibili/`、`secrets/extensions/<id>/`。拓展没有自己的文件目录。
   - **核心的订阅运行态只留中立的东西**：资料缓存、问题表（`problems` 按 code）。`fansBaseline` 退役，涨粉起点取粉丝时序第一条样本（⚠️ 以后要给粉丝时序加截尾，必须先把这个起点另存，否则截尾会悄悄改掉涨粉起点，Q19）；B 站的 `roomId`、关注同步结果搬进 B 站自己的状态（Q77）。
   - 设置是单文件分段，见 ADR-0021 决策 42；订阅合成一个文件，见 ADR-0021 决策 15。
    🔗 **2026-09-28**：问题表不再存盘，订阅运行态只留资料缓存（ADR-0025 决策 11）；内置集成不止 B 站，三个内置平台适配器要存 `state` / `secrets` 时照 B 站的样子放在 `runtime/<键>/`、`secrets/<键>/`，仍不设 `sources/`（ADR-0025 决策 9）。
9. **一个统一图库（Q63、Q75、Q27）**：
   - 位置在 `<代>/images/<sha256>.<ext>`；作品图、直播封面、头像、历史快照都引用它；
   - 原来的 `runtime/avatars/`、`history/img/` 取消；
   - 保留期清理时按引用清扫，引用方包括历史行、重推原件、资料缓存；
   - 迁移时把老图按 sha256 改名后硬链接进来。

   理由：交图、存图、清图都只剩一套做法。

   - **`ImageRef` 就是文件名 `<sha256>.<ext>`**（带扩展名）。扩展名按嗅探内容得出，是字节的纯函数，同一份字节永远同一个引用；读口、出图器、AI 看图拿到引用就知道 mime，不用列目录找文件、也不另存 mime（重推原件里的 `{ ref, mime }` 随 ⑱ 并成一格）；一条正则就能校验，顺带挡住路径穿越。被否的备选：引用只存 sha256 —— 每次读都要先查扩展名，或者另存一份 mime，多一处要保持一致的数据。
