# ADR-0005:应用内自主升级

- **状态**:**已实现并发版**(2026-09-01 前后经 `/grill-me` 拷问定案,随 v0.9.0-alpha.1 首发 2026-09-02;0.9.0 → 0.9.1 的正式渠道往返已真机验通)
- **记录方式**:⚠️ **事后追认** —— 据定案记录与已落地的实现整理,**非当时拷问的原文**。「决定了什么」与「为什么」可信,「当时的现场」不可考。
- **影响面**:`apps/server/src/boot.ts`、`apps/server/src/update/`、`apps/server/src/routes/update.ts`、`apps/web/src/components/update/`、`scripts/{build-update-payload,gen-update-keys,sign-update-manifest,revocation}.mjs`、`.github/workflows/{update-payload,revoke-update}.yml`
- **不影响**:Koishi / AstrBot 插件(两端已暂停,维护线见 `docs/agents/build-release.md`)

## 背景

独立端有 Docker 镜像与桌面安装包两种形态。换一个版本意味着用户去重拉镜像或重下安装包 —— 而这个项目的用户里有相当一部分是把它跑在 NAS、软路由、家用 NUC 上的,那道手续足以让他们停在某个旧版本上不动。

同时,一旦要做「应用内换代码」,就等于把**一条能执行任意代码的链路**开进了用户的机器。这个 ADR 的一半篇幅是在处理那条链路。

## 决策

### 形态

1. 发版时打一个**自包含载荷 zip**、签一份清单挂到 GitHub Release;客户端验签、下载、解进 `<dataDir>/versions/<版本>/`,**重启时由 `boot.mjs` 选中它**。安装包 / 镜像自带的那份**永远不动**,所以随时能退回去。
2. **`boot.mjs` 是单独一个 bundle 入口**,只牵 node 内建 + 选版那一小块。塞进 `index.mjs` 顶上不行 —— ESM 的 import 是提升的,那样会先把镜像那份服务端的整张模块图加载完,再加载一遍载荷那份,**内存直接翻倍**。
3. 选中之后是**同进程 `import()`,不是 spawn**:少一个常驻进程、不用转发信号,而且载荷里的 `import.meta.url` 指向它自己的目录 —— dashboard 资源与版本号因此自动跟着走。
4. 🔴 **`startStandaloneServer` 这个导出是向前兼容契约。** 镜像里的 `boot.mjs` 是冻住的,它得能启动任何未来版本的载荷。改名 = 老镜像上的用户更新完打不开。同理**不许往它的签名上加参数**,要传东西只能经 env。

### 信任

5. **两把 Ed25519 密钥,且必须从第一个发出去的版本起就都在信任列表里。** A 主用(进 CI secret),B 备用(**只在离线备份里,永远不进 CI**)。理由是信任列表**冻在已经发出去的那些安装里** —— A 泄露那天唯一的办法是用 B 签一版并把 A 踢出列表,而事后再加公钥救不了任何存量用户。
6. **签的是清单那个字符串,信封本身从不被签。** 展开成对象就要求验签时重新序列化,而 JSON 的重新序列化不唯一(键序 / 空白 / 数字写法 / unicode 转义)—— 两边差一点就验不过,且**完全查不出原因**。
7. 载荷本体只有**整包 sha256**,不做逐文件签名。
8. **清单带 `issuedAt`,客户端记住每个渠道见过的最大值**,比它旧的一律不收。光有签名不够 —— 签名只证明「这串字节我们签过」,不证明它是**当前**那一份,代理站可以永远回放一份签过的旧清单。两条一起,代理站才真的只剩「拒绝服务」这一种本事。
9. **空公钥列表 = 功能关着**,客户端明说「本构建未启用」,**不报成验签失败**。fork 出去自己构建的人默认落在这一档。
10. 信任根**不给配置入口** —— 能被配置改掉的信任根不是信任根。

### 渠道与加速

11. 清单挂在一个**滚动的 `update-channel` release** 上。不用 `releases/latest/download/`,因为它按定义指向最新的**正式**发布,预发布渠道就永远拿不到自己那份;也**不碰 `api.github.com`** —— 代理站不代理 API,而且 API 的回答上没有我们的签名。清单和载荷同域同前缀,用户填**一条**加速前缀就同时管住两者。
12. 正式版发布**同时刷 stable 与 alpha**(预发布渠道的用户也该拿到更新的正式版,否则会卡在某个旧 alpha 上);预发布只刷 alpha。
13. **默认直连,只能选一个加速前缀。** 内置名单只决定面板上给谁看,**不决定默认和谁说话** —— 硬编码一个第三方当默认,等于让每一个安装都去和它说话,它哪天挂了或易主,我们只能靠发新版本收回这个默认值。

### 面板

14. **打开面板就查一次,不定时。**
15. **自动下载默认开,但从不自动应用。** 下载是无副作用的(装进一个新的版本目录,不碰正在跑的那份);应用要重启服务,那一刻推送会断、直播监听会掉,**必须是用户按下去的**。
16. 按下「立即重启并应用」之后,页面**收不到任何消息**,所以「重启完了吗」由页面自己去问:按之前记下 `/api/health` 的 `startedAt`,之后每秒探一次,**只认 `startedAt` 变了的回答** —— 光「能连上」不算,旧进程优雅停机时还能连上好几秒。三种结局(换成了 / 起来了但版本不对 / 等满 90 秒)各有各的说法,一个不落。
17. 「有没有新版」「这一阶段怎么说」**只判一处** —— 概览说「有新版」而系统页说「已是最新」,就是两处各判一遍的下场。

### 撤回与自愈

18. 三道闸各管一批人:**服务端撤回**(重签清单、`revoked` 列上坏版本)、**客户端自愈**(`boot.mjs` 连续起不来到上限就判死、自动退回上一版)、**新鲜度**(重签让 `issuedAt` 变新,旧清单再也推不回来)。
19. 🔴 **`revoked` 与 `failed` 两份名单刻意分开。** 自愈那份的语义是「这一版起不来」,所以它起来之后会被放出来;而「厂商召回」不会因为它能启动就不成立。共用一份的下场是:撤回镜像自带那版之后,重启一次召回就被自己撤销了。
20. **自愈压过用户手动钉的版本** —— 否则退到一个也起不来的版本就是死局(进不去面板 = 拔不掉钉子)。
21. **只保留当前 + 上一版**,回退只退一步,不给版本列表。清理**只碰长得像版本号的目录**,外加我们自己的 `.staging-*` / `.old-*` 残留 —— `/data` 是用户挂出来的,他真的会往里丢东西。

22. ⛔ **重启不做成一颗常驻按钮 —— 它是某个动作的后果**(2026-09-10 主人拍板)。面板上没有「重启 BN」这个随时可按的入口:只有刚做完一件**确实需要重启**的事之后,才在那件事旁边就地提示一次,并在那一刻给出唯一一颗按钮。今天只有一种情形够格 —— **盖掉一份已经在跑的拓展**(它的代码 import 过,ESM 在这个进程里换不掉)。
    做法上它与「立即重启并应用」完全同一条路:优雅停机 + 退 0 + 决策 16 那套「只认 `startedAt` 变了的回答」,差别只在**为什么**关。所以服务端只留 `POST /api/system/restart`,**不开只读的判据口** —— 要不要给按钮,由做那件事的那个回话自己带上(`ExtensionInstallResponse.restart`)。
    🔴 **判据是「外面有没有人拉」,不是「哪一种构建」**:桌面外壳明确承诺见退出码 0 就拉起、容器靠 `restart:` 策略、`tsx watch` 只等文件变(实测)、裸 `node lib/index.mjs` 没人管。**判错的代价不对称** —— 说能、其实没人拉 = 用户按一下就把 BN 关了,而界面上只会显示连不上;说不能 = 少一个按钮。所以拿不准的一律算不能,而且**拉不起来时 POST 也要拦**(藏起按钮不等于没人发这个请求;旧标签页与 curl 都还在)。
    不能重启的那两档**要把原因写出来**:藏个按钮不解释,与功能坏了长得一模一样。
    (第一版曾把它做成系统页上的一节,同日按主人的话撤掉 —— 常驻的重启入口是在请用户拿它当锤子。)

## 明确不做(拷问中被否决的)

- **客户端下载后冒烟测试**(2026-09-04 主人拍板):CI 已经冒烟过、加上 sha256 校验足够,在用户机器上再起一次进程试跑,收益不抵复杂度。
- **开发版查更新**:`0.0.0-dev` / 读不到 package.json 时的兜底 `dev` 一律报 `disabled`(reason `dev-build`),服务端连网络都不碰。不挡的话开发时每次开面板都被提示「有新版」。
- **给用户一张历史版本列表**:想要更老的版本自己去下老镜像 / 老安装包,风险自负。
- **写一个 `CONFIG_SCHEMA_VERSION` 版本文件来保证回退安全**:旧构建根本不读它,兜底只能是迁移留下的 `.bak`。

## 后果

- 撤回一个坏版本走 `revoke-update` workflow(手动触发、默认 dry-run)。它**刻意不跑门禁** —— 这里一行代码都不发,只是把清单指回一个已经发布过的载荷;给一件本该几十秒的急事加十几分钟没有意义。
- **两把私钥都丢 = 存量用户再也收不到能验过签的更新。** 离线各存一份。
- macOS 自带的 `openssl` 其实是 LibreSSL,**不认 ed25519 而且退出码是 0** —— `-out` 指定的文件根本没被创建,下一条命令才报「文件不存在」,把人指向完全错误的方向。一律用 `scripts/gen-update-keys.mjs`。
- **`webDistDir` / `--web-dist` 一旦写死,前端就不跟着升级走了**(症状是「升完了界面没变」)。两端都已改成相对载荷入口就近解析。
- 🔗 **这套机制的两条性质后来成了拓展化的硬约束**:载荷是**全依赖内联的 bundle、旁边没有 node_modules**,所以第三方代码 import 不到 `@bilibili-notify/*`;而信任链是**硬编码两把公钥**,天生只服务「自家的下一个版本」。详见 ADR-0012。

## 仍未决 / 未验

- **撤回与自愈两条路真机没碰过** —— 只有单元测试。
- **装完拓展那句提示里的重启按钮(决策 22)真机一次没按过**:判据在四种环境里各是什么、按下去回不回得来,都只有单元测试。
- Windows 真机、桌面壳「sidecar 退 0 → 外壳拉起」、六个内置加速站(2026-09-02 凭经验列的,没逐个实测)。
