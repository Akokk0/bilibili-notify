# ADR-0017：推送失败后的人工重推 —— 历史行上的一颗按钮

- **状态**：2026-09-19 拷问四轮定案；**2026-09-20 全部落地**（七个切片，每片验红 + 剪线验红）。落地时有两条决策被实现推翻，已就地改写并标明原委（决策 1、16），**2026-09-20 随 v0.12.0 发布**,**真机未验**
- **记录方式**：拷问当场落的定案，不是追认
- **影响面**：`apps/server` 的历史仓（写入形状 + 一条按行 id 写补丁的新路径）、新的重推原件存储与它的 API、`apps/web` 的历史页、`packages/internal` 的历史 schema（`HistoryMessage` 多一个可选字段）。**`packages/push` 与两个引擎不动**
- **依赖**：[ADR-0011](0011-push-data-model.md)（推送数据模型）—— 行模型「一行 = 一次推送 × 一个目标」与四态都出自它；本份在它上面加一条人工重投的路径，不改它

## 背景

bot 离线期间推送失败，上线之后希望能补推。拷问中查实的六件事决定了这份定案的形状：

1. **失败标记已经在历史里**：行有 `status`（`failed` / `partial`），每条消息有 `result.ok` 与 `result.err`。再维护一份失败清单就是第二份真相。
2. 🔴 **历史里的 payload 是给人看的有损摘要，不是可重放的记录**：图集只剩一句「[图集 N 张]」、小程序卡只剩标题、composite 只留第一张图、`at-all` 段被写成**字面文字**「@全体」。拿它重发会发出一条与原文不同的消息 —— @全体 那条会真的把四个字发出去。
3. **既有重试是短程的**：目标不可达时退避重试、约 190s 就放弃。bot 离线几小时这种它救不了，所以这不是重复造轮子。
4. **bus 上没有「连接上线」事件**：自动重推要先造一个信号并接到每个 adapter 的重连路径上。
5. **`status` 是写入时算好存在盘上的，读侧不重算**：改判定规则只影响新写入与新补丁，老行不用迁移。
6. **被中止的消息在历史里根本不存在**：一条失败即中止该目标后续条，被中止的不进结果也不进历史。所以一次本该发 3 条的推送，可能在面板上只显示 1 条。

## 决策

### 重推的原料

1. **另存原件，不从历史重建**（背景 2）。存的是**整段 payloads**，含从没发出去的那几条（背景 6）—— 否则补不全。

   ⚠️ **原本写的是「失败那一刻另存」，实现时发现办不到**：一次推送分好几轮广播（下播卡 → 词云 → 总结），等到某一轮失败时，前几轮的原始 payload 早就只剩历史里的有损摘要了；而决策 8 的「重推全部」要的正是整行原料。改成**每次落行 / 追加时都留一份**（无目标行除外）。代价是已送达的行也占一份 json —— 但图是复用历史那份的（决策 3），一行就是几百字节，天花板仍是保留期。
2. **落盘，不放内存**。要解的场景是「离线一段时间后上线」，而这段时间里服务端重启完全可能（本项目自己就有应用内自主升级，升级即重启）。内存版会在最需要它的那一次恰好是空的。
3. **图复用历史已经写过的那一份**，只有历史丢掉的（图集第二张起、composite 的后续图）才额外写。
4. **保留期跟 `historyRetentionDays` 走同一个数**，不新开旋钮 ——「历史还在 = 还能重推」是最省解释的心智。另加一个总字节硬上限防炸盘，满了从最旧的丢；**它是保险不是偏好，不做成用户旋钮**。
5. **重推成功即删原件**；只补了一部分、或重推又失败的不删。

### 界面与手势

6. **按钮只长在 `failed` 与 `partial` 行上**。`no-targets` 不给 —— 那不是失败是没配目标，而且没有目标可发。
7. **不判断「哪些错不值得重试」**。面板如实显示 `err`，用户自己决定。
8. **两下完成，第二下即确认**：`failed` 行一颗钮（那一行本来就全没到，两个选项在这儿是同一件事）；`partial` 行点开给「重推全部」「只补没到的」两个选项加一个取消。不弹模态框 —— 误触的代价是群里多一条撤不回的消息，但一屏十几行弹窗太重。
9. **原件已经不在的行，按钮灰掉并说明原因**，不是把按钮藏掉。藏掉的话用户要么以为这行没失败过，要么以为功能坏了。

### 发送时的闸

10. **挡「这个目标还该不该收」**：routing 里已经没有它、目标或连接被停用 → 拒。与发送层每次重试前复检 routing 同源：用户已经取消了。
11. **不挡「现在是不是发消息的好时候」**：全局静音、免扰时段、特性总开关都不挡。这是用户**此刻按下的显式动作**，不是引擎自动推送；挡掉他只会以为按钮坏了。静音期间按钮旁如实说一句。
12. **目标不可达不挡** —— 那正是重推要解决的东西，让它走正常的退避重试。
13. **服务端按历史行 id 挡并发**：这一行正在重推就拒第二次。挡在服务端而不是只靠前端禁用 —— 两个标签页前端管不着，而后果是真的往群里多发一条。

### 历史怎么记

14. **追加进原行，不新开行，也不替换**。行模型不变；「失败过并被人工重推」是事实，排查时「什么时候失败、隔多久补上」正是最有用的信息。
15. **重推的消息带 `retryOf: <原消息序号>`**。序号就是稳定身份 —— 消息按序追加、从不重排删除。
16. **`computeStatus` 改成「每个原序号取它自己的最后一次结果」**：**每一号都有到了的结果**才 `delivered`，本体那一号没 ok 就是 `failed`。

    🔴 **它与决策 17 绑死，不是两条独立决策**。老算法判的是「有结果的那些都 ok」——决策 17 之后，那几条从没发出去的消息也落进行里（没有 `result`），只看有结果的那些，一行「本体到了、后面两条压根没发」会被算成**已送达**。只做 17 不做 16，面板上就会出现明明缺了两条却是绿的行。⚠️ **不能简化成「按 role 取最后一次」** —— 同一 role 下有多条时会把不同消息混成一个：补好 extra1 之后整行变绿，而 extra2 还躺着没送到。老行没有 `retryOf`，判定一个字不变。
17. **未发送的消息也落进历史行**（`result` 缺省，与 `no-targets` 行的每一条同形状）。否则按钮上的条数与展开看到的对不上；而「本来还有 2 条没发」今天是静默丢掉的，顺手补上。
18. **重推又失败就再追一条失败的**，按钮继续可按。不做「失败 N 次后禁用」——「试过两次都没成」正是用户判断该去修 bot 而不是继续按的依据。

## 明确不做

- **自动重推**（连接恢复后自己补发）。**容易 bug 复推**，而复推的代价是往群里重复发消息、撤不回。技术上还缺一个「连接上线」事件（背景 4）。手动这条打通后，自动只是在同一个地基上加一个触发器，将来要做不会白做。
- **私聊指令重推**。**很麻烦** —— 那是另一套入口（指令表、参数模型、权限），而手动按钮已经解决同一个问题。
- **另建一份失败清单**（数组 / 对象）。失败标记已经在历史里（背景 1），再存一份就是第二份真相，迟早漂。
- **从历史行重建要发的消息**。历史是有损摘要（背景 2），重建出来的与原文不是同一条。
- **只重推历史行里有的那几条**。数字是对上了，但第一条就失败时后面本该发的永远发不出去 —— 让按钮在最需要它的场景下办不成事。
- **替换掉失败的消息让行「干净」**。丢掉的是事实。
- **一张「哪些错不值得重试」的表**（决策 7）：它会在协议端改一次错误文案之后静默失效，而失效的方式是「本来能重推的行没有按钮」。
- **「失败 N 次后禁用按钮」**（决策 18）。
- **给重推原件单开一个保留期旋钮**（决策 4）。

## 后果

- **`HistoryMessage` 多一个可选字段 `retryOf`**。老行读出来是 `undefined`，按「不是重推」处理。它同时是展开逐条时那个「第 N 次尝试」标记的来源 —— 不用再开第二个字段。
- **行会变长**：3 条的行「重推全部」之后变 6 条，展开药丸上的数字会跳。认下，换来的是可追溯。
- **「重推全部」会把已经送达的也再发一遍**。那是用户显式选的那一档；`partial` 行的另一个选项就是为了避开它。
- **历史仓要开一条新路径：按已知行 id 写补丁**。现有的追加靠内存里那张有上限、重启即空的表找行，而重推往往发生在那之后；盘上的补丁行本来就是按行 id 认亲的，读侧不需要它。

  🔴 **补丁必须写进「原行那一天」的日文件**：读侧并补丁用的是一张**单文件局部**的 id 表，跨了日文件就找不到亲、整条补丁被静默丢掉 —— 症状是「点了重推，消息真的发出去了，面板上却什么都没变」。

- **重推成功会让趋势图上那一天的「失败数」回落**：`partial` 也算失败，行补绿成 `delivered` 之后按日聚合就少数一个。行数不变（追加不新开行）。这是对的 —— 补上了就不该继续算失败 —— 但它是个会让人疑惑的数字变动。

- **HTTP 不能同步等**：发送层光退避就最长约 190s，一行补 N 条是 N 倍。端点回 **202「收下了」**，消息在后台一条条补，进度经既有的 `history-updated` 回面板。
- **备份不带重推原件**。备份只收 globals / subscriptions / connections / targets，历史本来就不在里面。
- **写入侧变重一点**：未发送的消息要落行（决策 17），失败时要落原件。
- **开发版的截流不用另接**：重推走同一条 sink，自然被拦住。

## 仍未决

- **原件的总字节上限定多少**（决策 4 那半）。还没有真实数据支撑 —— 一次长离线到底会积多少条、卡片图平均多大，真机跑过一轮再定。**今天的天花板只有保留期**。
- **手动这一档够不够**。报告人原文三样都提了（自动 / 手动 / 指令），这一期只给手动；得去问他够不够用，答案决定将来要不要重开自动那条。
