# ADR-0001:一键备份 / 恢复用 6 位数字 PIN

- **状态**:**已实现**(2026-07-11 落 dev,7 个 commit)
- **记录方式**:⚠️ **事后追认** —— 据定案记录整理,非当时原文。
- **影响面**:`apps/server/src/backup/`、面板的备份 / 恢复一节

## 背景

一键备份要把机密一起带走:B 站 Cookie、AI 服务商的 key、各连接的凭据。这份文件一旦落到别人手里,等于把主人的 B 站账号和面板密码一起给了出去。

所以它必须加密。问题是**用什么加密** —— 长口令安全但记不住(而备份是低频操作,忘了口令等于备份作废),数字 PIN 好记但离线可爆破。

## 决策

1. **完整备份用 6 位数字 PIN 加密机密。** 最初拍的是 4 位,同日主人主动改成 6 位 —— 对齐 Windows Hello / macOS 的设备 PIN 长度。
2. 🔴 **这是主人在完全知情下做的选择。** 我明确陈述过短 PIN 的弱点:**离线暴力破解没有联网限流、没有锁定、没有实体二因子**,不像银行卡那样有硬件与风控兜着。主人的判断是:**PIN 是防手滑的便利锁,真正的保护是保管好文件本身。**
3. 6 位把离线搜索空间从 1 万抬到 100 万 —— **量级改善,性质不变**。
4. 🔴 **作为交换条件,导出完整备份的 UI 必须始终保留那句红字警告**:「此文件 = 你的 B 站账号与面板密码,请妥善保管、切勿外发;6 位 PIN 仅防手滑」。**这是主人接受该风险的前提,删不得。**

## 明确不做

- **换成长口令 / 强密码**:主人已经在知情下否决过。**不要再在后续会话里重新论证这一条**,除非主人主动提起。

## 后果

- 备份文件的安全性**取决于用户怎么保管它**,不取决于我们的加密强度。产品文案必须诚实地这么说 —— 那句红字就是这个诚实的载体。
- 脱敏备份(不带机密的那种)是另一条路,不受本 ADR 约束:它按**键名**脱敏(`token` 已在词表里),所以桥接那类新凭据不用加新规则。
