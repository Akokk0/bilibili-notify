# 写 CHANGELOG

发版流程的**必经一步**,不是可选的收尾。文件是 `apps/CHANGELOG.md`;基线(上一个发布点)= 最新 tag:`git tag -l 'v*' --sort=-creatordate | head -1`。

## 步骤

1. **定基线** — 见上文。完成:拿到一个具体的 tag / 版本。
2. **收集** — `git log <基线>..HEAD --oneline --no-merges`。完成:本批 commit 全部在手。
3. **筛掉用户感知不到的** — 每条 commit 判断用户是否感知得到(见「不写进 CHANGELOG 的」)。完成:每条 commit 都归了类,或被判为「不写」。
4. **归类成稿** — 按 `### Added` / `### Changed` / `### Fixed` 写进文件。完成:符合下方「写法」的每一条。
5. **拍板** — 版本号 + CHANGELOG 摘要给用户确认。完成:用户明确同意。**不要自己决定版本号。**

## `packages/*` 改了 ≠ 用户感知得到

共享包被改,不代表独立端用到了被改的那部分能力 —— 得去 `apps/` 里 grep 验证它是否真的用到了。判错的代价是**在 CHANGELOG 里向用户承诺一个他根本得不到的修复**,或者反过来漏掉一个他需要知道的破坏性变更。

## 不写进 CHANGELOG 的

用户感知不到的一律不写:CI / workflow、构建工具链、`docs/`、`chore`、测试、重构。CHANGELOG 是写给用户的,不是提交历史的镜像。

判据:**这条改动会改变用户看到的行为、装到的东西、或者要动的手吗?** 不会 → 不写。

### 本轮新功能的修复不写

**修的是本轮新加的功能 → 不写 Fixed / Changed 条目。** 判据一句话:**这个功能进过正式版吗?** 没有 → 它的修补都是「本来就该有的固有行为」,不是条目。

- **Why**:Fixed 条目的意思是「一个你已经在用的行为坏了、现在好了」。一个从没进过正式版的功能,正式版用户第一次见到它时它就长这样,给他们看「此前不这样,现在这样了」只会让人以为有一版是坏的;alpha 用户拿到的也是同一个功能的成品,不需要把打磨过程逐条念给他听。
- **How**:该功能的行为写在它自己的 **Added 条目**里,而且写的是**最终行为**。修补改变了先前 Added 条目里承诺过的说法时,回去改那条 Added 的措辞(它还没进过正式版,可以改),不新开 Fixed。
- **界线**:修的是**上一个正式版里已经有的**功能 → 照常写 Fixed。判断「新不新」看上一个正式版,不看上一个 tag:alpha.2 里修 alpha.1 才加的东西,同样不写。

## 正式版跟在 alpha 之后怎么写

1. **条目基线仍是最新 tag(那个 alpha)**,只列相对它的改动;**不按条目汇总 alpha 段的内容,hash 不重复出现**。alpha 各段留在下面就是历史,读者顺着往下翻。
2. **概述仍受「一到两句、120 字」约束**:说清正式渠道(`latest`)从哪个版本挪到这里,加上一个正式版之后最值得说的一两件事;「在哪几段」(点名 `X.Y.Z-alpha.N`)这种导航放进下面那段 ⚠️ 导读,不塞进概述。
3. **给从上一个正式版直接升上来的人一段导读**,固定写成「⚠️ **从 <上一个正式版> 直接升上来的主人请先看这段。**」+ 要点列表:每一条是**要动手的事**或**升级路径上的坑**,并指向具体的 alpha 段(「详见 `X.Y.Z-alpha.N`」)。有多条更新渠道的话,顺带说一句各渠道是否都会收到这一版。
4. **相对上一个 alpha 没有面向用户的改动时就直说**(「相对上一个 alpha 没有新的面向用户的改动,只是收尾」),不硬凑条目;见上面「本轮新功能的修复不写」。
5. 正式版段之后不动 alpha 段的结构;但 alpha 段里说错的、被后来推翻的说法照「发现上一版写错了就在新版里更正」的规矩处理。

## 概述段:一到两句、120 字以内、要动手的事另起一段

标题下第一段是**概述**,它不只是给读者看的:发版 workflow 会把它原样抽出来(去掉加粗 / 反引号 / 链接)签进更新清单的 `notes`,右下角「有新版」通知卡念的就是这句;公告的开场白也是它的女仆版。所以:

- **一到两句,只说本版最值得说的事**,平实口吻(同 CHANGELOG 其余部分,不换腔)。硬上限 **120 字**(去掉 markdown 之后数),超了 `update-payload` 在构建前那步直接红,tag 已经打了只能补版本。0.9.1 那段是超了的反例(三句,把 ⚠️ 和渠道说明都塞了进去);已发不改。
- **要动手的事项、升级路径上的坑另起一段**,以 ⚠️ 开头(0.9.0 那种写法),不进概述 —— 通知卡只念第一段,发布页正文贴整段,⚠️ 在那里才有位置展开。
- **一行写完**,别软换行(抽出来会按空格拼)。
- 写完就本地验一次,红了当场改,别等 CI:

```bash
node scripts/changelog-section.mjs --version <VERSION>            # 打印概述;找不到 / 为空 / 超长退 1
node scripts/changelog-section.mjs --version <VERSION> --part section   # 发布页正文会贴的整段
```

## 写法

风格(Keep a Changelog):

```md
## [0.2.0] — 2026-07-11

<概述:本版最值得说的一两件事,120 字以内,一行写完>

⚠️ <要动手的事项 / 升级路径上的坑,另起一段;没有就不写这段>

### Added

- <面向用户的描述> (hash)

### Fixed

- <面向用户的描述> (hash, hash)

---
```

- **版本标题** `## [版本] — YYYY-MM-DD`,版本之间用 `---` 分隔。
- **commit hash 放条目末尾的括号里**,多个用逗号分隔。
- **写用户能感知的事,不写实现**。「玻璃片透明度改回默认存不下去」是用户的话;「`JSON.stringify` 丢弃 `undefined` 键」是我们的话。
- **一个功能一条,不按 commit 拆**。备份/恢复横跨 7 个 commit,写成一条,hash 全列。
- **坏了就说坏了**。「这个功能对用 QQ 官方机器人的人从第一天起就是坏的」——不粉饰、不含糊,用户需要知道自己是不是受影响的那一个。
- **发现上一版 CHANGELOG 写错了,在新版里更正**。alpha.8 漏列了 `-image`,照着它操作的用户会把一个已经无法工作的插件留在原地 —— 所以 alpha.9 里明确更正。错误不会因为发出去了就消失。
