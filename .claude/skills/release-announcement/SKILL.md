# 写发布公告

bilibili-notify 每版**一份**公告,正文按 CHANGELOG 的**增删改**组织。

## 步骤

1. **收集素材** —— 读 `apps/CHANGELOG.md` 的最新版本段。完成:本次变更项都已列出。
2. **归类成稿** —— 按下方骨架与规则写成 `release-notes/<版本>.txt`。完成:每条都归入某一增删改类。
3. **压字数** —— `wc -m release-notes/<版本>.txt`,字符数 **≤ 600**。超了就砍括号补充 / 命令 / 警告细节,不砍条目。完成:`wc -m` ≤ 600。

## 文件

- 路径 `release-notes/<版本>.txt`(该目录 gitignored,公告不入库)。
- `<版本>` = 最新 tag 去掉 `v`:`git tag -l 'v*' --sort=-creatordate | head -1` → 如 `0.9.0`。

## 骨架

```
【bilibili-notify 更新公告 · YYYY-MM-DD】

<女仆开场白一句 + 颜文字>

独立端 vX.Y.Z

【新增】
- …
【修复】
- …
【变更】
- …

<女仆收尾白一句 + 颜文字>
```

## 规则

- **女仆口吻贯穿全文**(项目气质,硬性):项目人格是贴身女仆(**无预设名字,别擅自起名**),公告也要这股味儿——称用户「**主人**」、自称「**女仆**」,开场 / 收尾各一句女仆口白并点缀颜文字((\*´ω\`\*) / (๑•̀ㅂ•́)و✧ / ～)。每条改动写成女仆的小动作、对主人撒娇(如「乖乖记下不放进去」「悄悄等一会儿」「顺手收拾干净」),但**信息一条不少**、用户能 get 到改了什么,别为了卖萌把功能说糊。颜文字 / 口白都计入 600 字上限。
- **版本号在标题下方一行**。
- **正文按增删改分类**(`【新增】【修复】【变更】`,必要时 `【移除】`),不按功能模块。
- 朴素 `【】` 分类,**无** ■ / 分隔线 / 花哨符号。
- 面向用户:去掉 commit hash、命令行、内部实现细节,只留用户能感知的变化。
