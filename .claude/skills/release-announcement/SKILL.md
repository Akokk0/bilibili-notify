# 写发布公告

bilibili-notify 每版**一份**公告,正文按 CHANGELOG 的**增删改**组织。

## 步骤

先确定本次本体版本：优先使用用户指定或当前发行流程已确认的版本；未指定时才从最新 `v*` tag 取版本。用 `vp exec node scripts/changelog-section.mjs --version <VERSION> --part section` 读取对应段。本流程只处理本体公告，SDK、创建器和拓展使用各自的发行资料。

确认材料对应所选版本后，按下方骨架写 `release-notes/<版本>.txt`。内容、标题和文件名使用同一版本；未打 tag 的候选也用已确定的候选版号。

`wc -m` ≤ 600；超了砍括号补充、命令和警告细节，不砍条目。

## 文件

- 路径 `release-notes/<版本>.txt`(该目录 gitignored,公告不入库)。
- `<版本>` = 上一步选定的版本；默认 tag 的查法是 `git tag -l 'v*' --sort=-creatordate | head -1`，去掉前缀 `v` 后使用。

## 骨架

```
【bilibili-notify 更新公告 · YYYY-MM-DD】

<开场白:CHANGELOG 概述段的女仆版 + 颜文字>

独立端 vX.Y.Z

【新增】
- …
【修复】
- …
【变更】
- …

<女仆收尾白一句 + 颜文字>
```

## 规则

- **女仆口吻贯穿全文**(项目气质,硬性):项目人格是贴身女仆(**无预设名字,别擅自起名**),公告也要这股味儿——称用户「**主人**」、自称「**女仆**」,开场 / 收尾各一句女仆口白并点缀颜文字((\*´ω\`\*) / (๑•̀ㅂ•́)و✧ / ～)。每条改动写成女仆的小动作、对主人撒娇(如「乖乖记下不放进去」「悄悄等一会儿」「顺手收拾干净」),但**信息一条不少**、用户能 get 到改了什么,别为了卖萌把功能说糊。颜文字 / 口白都计入 600 字上限。
- **开场白 = CHANGELOG 该版概述段的女仆版**:同一句话换腔(称主人、女仆小动作),信息不增不减 —— 概述已经是「本版最值得说的一两件事」,通知卡上念的也是它,公告别另起炉灶再总结一遍。
- **版本号在标题下方一行**。
- **正文按增删改分类**(`【新增】【修复】【变更】`,必要时 `【移除】`),不按功能模块。
- 朴素 `【】` 分类,**无** ■ / 分隔线 / 花哨符号。
- 面向用户:去掉 commit hash、命令行、内部实现细节,只留用户能感知的变化。
