# 写发布公告

每轮发行交付一份公告。BN 本体和官方拓展同轮更新时，将本轮更新合在同一份公告里，先写本体，再写各拓展，各用自己的版本行。

## 步骤

1. **确定本轮发行对象和版本。** 使用用户指定或本轮发行流程已确认的全部对象。只调用本技能且没有发行对象时，默认写 BN 本体。优先用已确定的版本，否则取该对象最近创建的发行 tag。官方拓展用清单里的 `id`，如 `douyin` 或 `bridge`。
2. **逐一读取对应版本。** 用 `vp exec node scripts/changelog-section.mjs --file <CHANGELOG> --version <VERSION> --part section` 读取每个对象的准确版本段。已发布版本可从对应 tag 读取更新日志，待发版本用已确定版本的工作区日志。缺少某个版本段时指出缺项，等对应日志补齐再写。保留完整版本后缀，如 `-alpha.3`。
3. **交付一份公告。** 按下方骨架写入一个草稿文件，逐一核对版本行与该对象的日志段。用 `wc -m` 检查整份公告不超过 600 字，超出时压缩括号补充和措辞，保留每项用户可感知的变化。

## 对象与版本

| 对象 | CHANGELOG | 发行 tag | 公告版本行 |
| --- | --- | --- | --- |
| BN 本体 | `apps/CHANGELOG.md` | `v<VERSION>` | `vX.Y.Z` |
| 官方拓展 | `extensions/<id>/CHANGELOG.md` | `extension/<id>@<VERSION>` | `ext-<id> vX.Y.Z` |

`<VERSION>` 是去除 tag 前缀后的完整版本号。抖音公告的版本行例如 `ext-douyin v0.1.0-alpha.1`。

草稿存入 Git 忽略的 `release-notes/`。含 BN 本体时用 `<本体版本>.txt`。只有官方拓展时，用 `ext-<id>-<VERSION>` 作文件名，多项按拓展 ID 排序并以 `_` 连接，末尾加 `.txt`。

## 骨架

```
【bilibili-notify 更新公告 · YYYY-MM-DD】

<根据本轮 CHANGELOG 概述写一句女仆开场白和颜文字>

<第一个发行对象的版本行>

【新增】
- …
【修复】
- …
【变更】
- …

<其他发行对象的版本行与各自的改动>

<女仆收尾白一句 + 颜文字>
```

## 规则

- **女仆口吻贯穿全文**(项目气质,硬性):项目人格是贴身女仆(**无预设名字,别擅自起名**),公告也要这股味儿——称用户「**主人**」、自称「**女仆**」,开场 / 收尾各一句女仆口白并点缀颜文字((\*´ω\`\*) / (๑•̀ㅂ•́)و✧ / ～)。每条改动写成女仆的小动作、对主人撒娇(如「乖乖记下不放进去」「悄悄等一会儿」「顺手收拾干净」),但**信息一条不少**、用户能 get 到改了什么,别为了卖萌把功能说糊。颜文字 / 口白都计入 600 字上限。
- **开场白沿用本轮 CHANGELOG 概述的重点**，换成女仆口吻，保留原意。
- **每个对象以单独一行版本号开头**，使用表中的格式并保留预发布后缀。版本行下面写该对象的改动。
- **正文按增删改分类**。将 `Added`、`Fixed`、`Changed`、`Removed` 分别写成 `【新增】`、`【修复】`、`【变更】`、`【移除】`。仅展示有内容的分类。某个版本只有概述时，用概述交代它的变化。
- 朴素 `【】` 分类,**无** ■ / 分隔线 / 花哨符号。
- 面向用户:去掉 commit hash、命令行、内部实现细节,只留用户能感知的变化。
